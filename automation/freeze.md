# freeze — 수용 기준 테스트 동결 (하네스 중립 명세)

구현 전에 수용 기준 테스트를 **독립 작성자로 파생**하고, 기계 검증을 통과시킨 뒤 **동결**한다.
동결된 테스트는 구현 루프 중 수정할 수 없으며, 위반은 사후 감사로 탐지된다.

> **이 파일은 하네스 중립 「진실의 원천」이다.** 직접 실행 대상이 아니라, 동결이 필요한 상위 절차가 호출한다:
> - `/implement` (`.claude/commands/implement.md` Phase 2·4) — 명세 출처는 `docs/specs/<번호>`
> - `/problem` (`.claude/commands/problem.md` Phase 4) — 명세 출처는 Phase 1에서 확정된 해결책 상세
>
> 두 호출자의 차이는 **명세가 어디서 오는가**뿐이다. 아래 절차는 양쪽에서 동일하다.

## 원칙

**심판(테스트)과 선수(구현)를 같은 에이전트가 만들지 않는다.** 같은 에이전트가 둘 다 만들면
스펙 오독이 테스트와 구현 양쪽에 복제되어 서로를 통과시킨다. 테스트는 Codex가 명세에서 독립
파생하고, 구현 하네스는 **스텁 준비·리뷰·동결**만 담당한다 — assertion을 직접 수정하지 않는다.

Codex를 쓸 수 없으면 구현 하네스 단독 폴백으로 진행하되, **동결 이하의 절차는 모드와 무관하게
동일하다** — 동결의 가치 절반(구현 루프 중 테스트 변조 방지)은 작성자 분리 없이도 성립한다.

## 호출 파라미터

상위 절차가 아래를 확정한 뒤 이 문서의 절차에 진입한다.

| 파라미터 | `/implement` | `/problem` |
|---|---|---|
| **명세** | 스펙 전문 + §링크한 architecture.md 섹션 | Phase 1에서 확정된 해결책의 작업 상세 |
| **작업 ID** | 스펙 번호 (예: `18`) | 이슈 번호 (예: `52`) |
| **동결 단위** | 스펙 1개 = 1 단위 | `[API]` 작업 1개 = 1 단위 (N개 가능) |
| **참조 패턴 파일** | 동일/유사 도메인의 기존 테스트 1~2개 전문 | 동일 |

**동결 단위가 여러 개면 1~5번을 단위마다 반복**하고, 6~8번(목록·커밋·SHA)은 전 단위 완료 후 **1회**
수행한다. 선택된 작업이 전부 `[비API]`여서 동결 단위가 0개이면 이 절차 전체를 스킵한다.

상태 파일은 호출자와 무관하게 `.cure-implement/`(git-ignored)를 공유한다 — PreToolUse 훅
(`.claude/hooks/freeze-test-files.sh`)이 이 경로를 참조하므로 하네스별로 나누지 않는다.

## 절차

1. **스텁 준비(구현 하네스)**: 컴파일에 필요한 최소 시그니처(서비스 메서드·DTO 뼈대·모듈 배선)와
   fixture 컨벤션만 만든다. **로직 금지.** 인터페이스 시그니처는 아키텍처 결정이므로 구현측이
   소유한다 — 테스트 작성자에게 맡기면 코드베이스 컨텍스트가 가장 적은 에이전트에게 설계권이 넘어간다.
   스텁은 **동결 커밋과 분리해 먼저 커밋**한다(`[TEST/#<작업 ID>] 스텁 준비`) — 동결 커밋에
   테스트·fixture만 남아야 감사가 파일 목록을 동결 커밋 자체에서 복원할 수 있다.

2. **테스트 명세 프롬프트(구현 하네스)**: `.cure-implement/<작업 ID>-test-prompt.md`에 작성 —
   명세 전문, 수용 기준별 검증 포인트, 참조 패턴 파일 경로(BE: `test/auth.e2e-spec.ts`,
   FE: `src/shared/api/http.test.ts`), 스텁 시그니처, 출력 파일 경로, 그리고 다음 3개 필수 문구:
   - **"테스트·fixture 외 파일 수정 금지"**
   - **"모든 테스트는 스텁 상태에서 실패해야 한다"** (이미 통과하는 테스트는 구현을 검증하지 못하는 공허 테스트)
   - **"어떤 셸 명령도 실행하지 말고 파일 작성만 하라"** — 컴파일·Discovery·RED 검증은 전부 호출측
     (5번 게이트)이 수행한다. codex가 검증 프로세스(tsc·jest 등)를 띄우면 실행 시간이 폭증하고
     프로세스 트리가 호출 경계를 넘어 살아남아, **강제 종료 후에도 파일이 뒤늦게 착지해 동결 무결성을
     오염**시킨다 (9단계 실증 — loopin problem.md의 "복귀 실패" 문제와 같은 뿌리)

3. **Codex 호출(구현 하네스)** — 4중 방어 + 자연 종료:
   ```bash
   # timeout은 있을 때만 상한 래핑. macOS 기본엔 timeout/gtimeout이 없으므로 없으면 그냥 실행 —
   # 최종 backstop은 하네스의 명령 실행 timeout이다. perl alarm 등 강제 kill 금지.
   TO=""; command -v timeout >/dev/null && TO="timeout 480"; command -v gtimeout >/dev/null && TO="gtimeout 480"
   $TO codex exec --sandbox workspace-write -C <대상 레포> \
     --ephemeral \
     -m gpt-5.6-sol \
     -c model_reasoning_effort="xhigh" \
     -c mcp_servers='{}' \
     --color never \
     < .cure-implement/<작업 ID>-test-prompt.md \
     > .cure-implement/<작업 ID>-codex.log 2>&1
   ```
   - 프롬프트는 반드시 **stdin 리다이렉트(`< file`)** — positional 인자로 주면 stdin 대기 hang
   - 출력은 **파일 리다이렉트** — 파이프 상속 hang 방지. codex 출력에 파이프(`| tail` 등) 금지
   - **강제 kill(perl alarm·SIGALRM) 금지** — codex는 "파일만 쓰는 작업"이라 2번 문구가 지켜지면
     자연 종료한다. 조기 사살은 orphan 작업의 **지연 파일 착지**를 만들어 이후 커밋·동결을 오염시킨다.
     오래 걸리면 백그라운드로 돌려 세션을 묶지 않고 완료 통지 후 점검한다
   - **완료 판정은 exit code가 아니라 산출물로**: 로그 말미의 완료 응답(파일 목록·tokens used)과
     출력 파일 존재를 확인한다. timeout으로 끊겼어도 "파일은 이미 디스크에 있을 수 있다" — 실패로
     판정하기 전에 반드시 파일을 점검하고, **재시도 전 `pgrep -fl "codex exec"`로 잔존 프로세스를
     확인**한다(살아 있으면 완료를 기다린다 — 죽이거나 병행 재시도하지 않는다)
   - **모델·effort 모두 플래그로 명시 고정(`gpt-5.6-sol`/`xhigh`)** — config 편차로 심판 품질이
     조용히 열화되는 것을 막는다. xhigh는 사고 단계가 수 분 이상 길 수 있으나, 위의 "파일만 작성·자연
     종료·산출물 기준 판정" 전제에서 이는 hang이 아니라 정상 대기다. **핀 모델 미가용**(model not
     found류) 시 기본 모델(`-m`·effort 제거)로 1회 재시도하고 동결 커밋에 사용 모델을 명시한다
   - 실패 시 1회 재시도 → 그래도 실패면 **구현 하네스 단독 폴백** — **동결 포함 절차 동일**,
     동결 커밋에 `작성: Claude 단독` 명시. 이때 자기 리뷰는 독립성이 없으므로 5번 기계 게이트가 주
     방어선이 된다. **폴백 착수 전 잔존 codex 프로세스가 없음을 확인**한다 — 뒤늦은 착지와 폴백
     산출물이 경합하면 동결 대상이 오염된다

4. **리뷰(구현 하네스)** — 구현자 관점 개입 금지, 다음만 검사:
   - ① 수용 기준 전 항목이 커버되는가
   - ② **공허 통과** 가능성(미구현 라우트의 404 등으로 이미 통과하는 테스트)이 있는가
   - ③ 명세에 없는 가정을 추가했는가
   - ④ `git status`로 테스트·fixture 외 파일 무변경 확인
   - 문제 발견 시 프롬프트를 보강해 **Codex에 재작성 요청** — 구현 하네스가 assertion을 직접 고치지
     않는다. 컴파일 오류 등 기계적 수정만 허용하며 커밋 메시지에 기록한다.

5. **동결 게이트 — 3계층 기계 검증(구현 하네스)**. 4번 리뷰는 정성 검사라 커버리지·가정을 보고,
   이 게이트는 기계 검사다 — 둘은 보완재. 세 계층 모두 통과해야 동결한다:
   - ① **Discovery**: `pnpm test -- <신규 spec 경로>`(e2e는 `pnpm test:e2e -- <경로>`) 출력에
     신규 테스트 파일이 실제로 잡히는지 확인 — "No tests found"는 러너 패턴 불일치로, 영원히 조용히
     통과(스킵)되는 파일이라는 뜻이다
   - ② **빌드 GREEN**: `pnpm build && pnpm lint` 통과 — 동결 커밋은 이후 구현의 base이므로
     컴파일되는 커밋이어야 한다
   - ③ **실행 RED (테스트 단위)**: **모든 테스트가 개별적으로** 실패하는지 확인한다. 스위트 단위의
     "전부/대부분 실패"로 만족하지 않는다 — 스텁 상태에서 **통과하는 테스트를 기계적으로 열거**하고,
     건별로 정당화되지 않으면 Codex에 재작성 요청한다. 스텁(= 아무것도 안 하는 구현)을 죽이지 못하는
     테스트는 정의상 공허 테스트다. 특히 e2e에서 **미구현 라우트의 404로 우연히 통과하는 테스트**
     (리뷰 ②의 함정)가 여기서 기계적으로 걸린다. 부트스트랩 실패·컴파일 에러로 죽으면 RED가 아니라
     broken — 수정 후 재검증한다

6. **동결 커밋**: `[TEST/#<작업 ID>] <요약> 수용 기준 테스트 동결 (작성: Codex)` — 폴백 시
   `작성: Claude 단독`, 기계적 수정·모델 폴백이 있었으면 사유 병기. **동결 커밋에는 테스트·fixture만
   포함**한다(스텁은 1번에서 별도 커밋 완료).

7. **동결 등록(훅+감사 기준)**:
   - 테스트 파일 경로(레포 루트 기준 상대)를 `.cure-implement/frozen-tests.txt`에 한 줄씩 기록 —
     즉시 PreToolUse 훅이 해당 파일의 Edit/Write를 차단한다(예방). **절대 경로로 기록하면 워크트리
     (다른 루트 디렉토리)에서 훅이 매칭하지 못한다.**
   - `git rev-parse HEAD > .cure-implement/frozen-commit.txt` — 감사 기준 SHA. 재동결 시 갱신한다
   - `.cure-implement/`는 git-ignored라 이 상태 파일들은 변조 가능하다 — 감사의 불변 기준은 목록
     파일이 아니라 **동결 커밋 자체**다(아래 「사후 감사」 참조)

8. **이후 구현 중 동결 테스트 수정 금지.** **기본 추정은 구현 결함이다** — 동결은 "테스트가 맞다"는
   추정이므로 입증 책임은 항상 구현 쪽에 있다. 수정하고 싶어지면 그것은 명세 결함 신호다 → 호출자의
   명세 수정 규칙으로 회귀한다(명세 수정 → Codex 재파생 → 재동결 + `frozen-commit.txt` 갱신, 판단
   사유를 커밋 메시지에). 훅은 Edit/Write만 막으므로 Bash 우회 편집(`sed -i` 등)은 사후 감사가 잡는다.

## 이의 제기 (TEST-DISPUTE)

구현이 동결 테스트를 통과시키지 못할 때, **기본 추정은 구현 결함**이다. 그럼에도 디스퓨트가
성립하면 3갈래로 분류한다:

| 분류 | 처리 |
|---|---|
| **구현 결함** (기본값) | 구현을 수정한다 |
| **테스트 결함** (명세 오독) | 확정된 해석으로 Codex 재파생 → 재동결 |
| **명세 결함** (수용 기준이 모호·모순) | 명세를 먼저 고치고 재파생 → 재동결 |

- 테스트/명세 결함으로 판단되면 `⚠️ TEST-DISPUTE` 라벨과 함께 **테스트 이름, 명세 근거, 판단 이유,
  분류**를 사용자에게 보고하고 **확인을 대기**한다. 사용자 확인이 곧 명세 확정 행위다.
- 승인 시 해당 파일만 `frozen-tests.txt`에서 제거 → 수정 → **완료 즉시 목록에 다시 추가하여 재동결**
  한다(노출 시간 최소화). 재동결은 새 커밋으로 남기고 `frozen-commit.txt`를 갱신한다:
  `[TEST/#<작업 ID>] TEST-DISPUTE 승인 반영 — 재동결 (<판단 사유 요약>)`.
  **판단 사유를 커밋 메시지에 남긴다** — 승인 이력과 근거가 히스토리에 남아야 사후 추적이 가능하다.
- 감사 기준은 항상 **최신 동결 커밋**이 되어, 승인된 수정이 사후 감사에서 변조로 오탐되지 않는다.

> **에이전트가 사용자 확인을 대기할 수 없는 경우**(병렬 워크트리 등): 해당 작업의 구현을 중단하고
> (커밋하지 않음) **그 작업에 의존하는 후속 작업도 함께 중단**한다 — 미구현 스텁 위에 후속 작업을
> 쌓으면 잘못된 전제 위의 구현이 된다. 독립적인 나머지 작업만 진행하고, 완료 보고에 디스퓨트 항목과
> 중단된 작업 목록을 포함한다. 후속 처리는 메인 세션이 통합 직후 수행한다.

## 사후 감사

동결이 있었던 모든 실행에서 수행한다. 훅(예방)은 Edit/Write 도구만 막으므로 **Bash 우회 편집은 이
감사로만 탐지된다** — 훅=예방, diff=감사, 두 층이 필요하다.

```bash
FC=$(cat .cure-implement/frozen-commit.txt)
git diff-tree --no-commit-id --name-only -r "$FC"   # 목록 복원 (동결 커밋엔 테스트·fixture만 있다)
git diff "$FC" -- <복원한 목록>                       # 반드시 비어야 한다
```

- 감사 파일 목록은 워킹 트리의 `frozen-tests.txt`(변조 가능)가 아니라 **동결 커밋에서 복원**한다 —
  목록 파일에서 줄을 지우는 것만으로 감사 범위에서 빠지는 순환을 끊는다.
- diff가 비어있지 않으면 **중단하고 사용자에게 보고**한다.
- 워킹 트리의 `frozen-tests.txt`가 커밋된 원본과 다르면 그 자체도 이상 신호이므로 함께 보고한다.
- **감사는 항상 마지막 코드 변경 뒤에 온다.** 수정 루프·디스퓨트 처리가 모두 끝난 뒤 실행하고,
  감사 이후 코드가 다시 바뀌면 **재실행**한다. 감사를 수정 루프 앞에 두면, 우회 편집의 유혹이 가장
  강한 구간(RED가 풀리지 않는 수정 루프)이 무방비가 된다.

## 동결 해제

`.cure-implement/frozen-tests.txt`·`frozen-commit.txt` 삭제가 해제다. **머지(또는 배포) 성공 후**
에만 수행한다 — 실패로 코드를 재수정하는 동안은 동결을 유지해 테스트를 계속 보호한다.

`.cure-implement/`의 나머지 파일은 성격에 따라 처리한다: `<작업 ID>-test-prompt.md`·`-codex.log`는
**재생성 가능한 로그**라 사후 부검(Codex가 짠 RED 테스트가 이상할 때 근거 추적)에 쓰이므로 남기고,
실제 코드 내용을 담은 **데이터 스냅샷**은 목적을 다하는 즉시 삭제한다.
