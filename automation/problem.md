# problem — 문제 분석부터 배포까지 (하네스 중립 명세)

운영 중 발생한 문제를 분석해 해결책을 제시하고, 사용자가 선택한 해결책을 구현해 배포까지 완료한다.
브랜치명에 `#`이 포함되므로, 모든 git/gh 명령에서 브랜치명은 반드시 따옴표로 감싼다.

> **이 파일은 하네스 중립 「진실의 원천」이다.** 직접 실행 대상이 아니라 진입 어댑터를 통해 실행된다:
> - Claude Code → `.claude/commands/problem.md`
>
> 하위 절차는 다른 중립 명세를 호출한다: 테스트 동결은 `automation/freeze.md`,
> 배포는 `automation/ship.md`(→ `automation/pipeline.md`).

## 이 문서의 위치 — 단일 진입점

**운영 중 변경은 무조건 여기서 시작한다.** `/implement`는 spec이 이미 존재하는 계획된 스텝의
진입점이지, 사람이 고르는 갈림길이 아니다.

그 이유는 **버그 리포트 시점에는 원인을 모르기 때문**이다. "로그인이 가끔 풀린다"가 토큰 만료
설정값 문제인지 refresh rotation 정책의 결함인지는 진단해봐야 안다. 그런데 하네스 선택은 그
답에 의존한다 — 따라서 **라우팅은 진단 뒤(Phase 1.5)에 기계적으로 판정**하며, 사람이 사전에
고르지 않는다.

## Preflight

1. `gh auth status` — 인증 실패 시 **중단**
2. `git status --short` — 비어 있지 않으면 기존 변경사항을 임시 보관한다:
   - `git stash push -u -m "problem-preflight-stash"` (untracked 포함)
   - `HAS_STASH=true` 플래그 설정 (비어 있으면 `false`)
3. `git checkout dev && git pull origin dev` — 항상 최신 dev에서 시작
4. `HAS_STASH=true`이면 기존 변경사항을 dev 위에 복원한다:
   - `git stash pop` — 충돌 시 해결 전 `git stash show -p --include-untracked "stash@{0}"`를
     `.cure-implement/preflight-stash.patch`로 백업한다(`-u`로 stash한 untracked까지 포함해야
     데이터 손실이 없다). 충돌 파일을 자체 해결한 뒤 진행하고, 해결 내역을 사용자에게 보고한다.
   - 이후 Phase는 기존 변경사항이 워킹 트리에 있는 상태로 진행된다 (Phase 3에서 WIP 커밋으로
     승격되어 워킹 트리가 clean해진다)

## Phase 1: 문제 분석 & 해결책 제시

> **단순 변경 스킵**: 사용자가 구체적인 변경 내용을 직접 명시한 경우(예: "토큰 만료 30분으로
> 변경해줘") Phase 1을 스킵하고 단일 작업으로 구성해 Phase 1.5로 직행한다.

1. 제시된 에러 로그·문제 상황을 분석한다.
2. 관련 코드를 탐색해 원인을 파악한다.
3. 해결책을 번호와 함께 제시한다. 하나의 해결책 안에 API 변경과 비API 변경이 섞일 수 있으므로
   **해결책 내부를 작업(task) 단위로 분리**한다.

   ```
   해결책 N: [한 줄 요약]
   ├─ 작업 N-a [API]    변경 내용    | 영향 파일: src/domain/auth/service/auth.service.ts
   ├─ 작업 N-b [비API]  변경 내용    | 영향 파일: docker/gcp/compose.yml
   └─ 작업 N-c [API]    변경 내용    | 영향 파일: ...
   위험도: 낮음 / 중간 / 높음
   ```

   작업 분류 기준:
   - `[API]`: controller / service / repository / dto / persistence 스키마 / mapper 변경 포함
     → Test-First 절차 (`automation/freeze.md`)
   - `[비API]`: 설정, 문서, 인프라, 유틸, 빌드·배포 스크립트 → 일반 코드 변경 절차

   **영향 파일 목록은 Phase 1.5의 입력이므로 빠짐없이 적는다.**

4. **사용자 확인 대기** — 적용할 해결책 번호 선택 요청 (예: "1, 3번 적용")

## Phase 1.5: 라우팅 판정 (기계 검사)

선택된 해결책의 **영향 파일 전체**를 아래 게이트에 대조한다. 사람의 해석이 아니라 경로 매칭이다.

| 게이트 | 경로 패턴 (BE 기준 — FE는 해당 레포의 대응 경로) |
|---|---|
| **계약** | `src/**/dto/**`, `src/**/controller/**`, `openapi/*.json`, `src/global/common/exception/error-code.registry.ts` |
| **보안** | `src/global/security/**`, `src/domain/auth/**` |
| **새 도메인** | `src/domain/<기존에 없던 디렉토리>/` |

**하나라도 걸리면 이 절차를 중단하고 `docs/specs/` 작성 → `/implement`로 승격**한다. 중단 시점에는
아직 이슈·브랜치를 만들지 않았으므로(Phase 3 이전) 정리할 잔재가 없다.

- 걸리지 않으면 Phase 2로 진행한다.
- **오탐은 안전한 방향이다**: DTO 파일을 건드렸지만 내부 rename이라 계약이 그대로인 경우, spec을
  한 번 더 쓰는 비용이 발생할 뿐이다. 진짜 계약 파괴 여부는 `pnpm openapi:export` + PR의
  `openapi-breaking` job이 최종 판정한다 — 이 게이트는 그 앞단의 값싼 필터다.
- 판정 결과(걸린 게이트 / 통과)를 사용자에게 **한 줄로 보고**한 뒤 진행한다.

## Phase 2: 의존성 분석 & 실행 계획

1. 선택된 해결책의 모든 작업을 평탄화해 목록을 만든다.
2. 작업 간 의존성을 분석한다:
   - **같은 파일 수정** → 순차
   - **같은 도메인의 연관 로직 변경** → 순차
   - **서로 다른 도메인·파일을 독립 변경** → 병렬 가능
3. 실행 계획을 보고한다 (병렬 그룹 A/B, 순차 그룹 C 형태로 그룹핑, 각 작업의 타입과 절차 명시).
4. 보고 후 **사용자 확인 없이** 즉시 Phase 3으로 진행한다.

## Phase 3: 이슈 & 브랜치

코드 변경 **전에** 이슈와 브랜치를 만든다 — 병렬 워크트리의 base가 필요하기 때문이다.

1. 변경 성격에 맞는 타입을 고른다 (`automation/ship.md` Phase 1의 타입 테이블과 동일):
   `[FEAT]` `feat/` · `[FIX]` `fix/` · `[BUG]` `bug/` · `[CHORE]` `chore/` · `[REFACT]` `refact/` · `[DOCS]` `docs/`
2. `gh issue create` — 제목 `[TYPE] 설명`. 본문은 `.github/ISSUE_TEMPLATE/<타입>.yml`의 `body:`
   각 항목 `label`을 마크다운 헤더로 매핑하고 `required: true` 항목을 Phase 2의 실행 계획으로
   빠짐없이 채워 `--body`로 전달한다 (폼 파일 자체를 본문으로 붙여넣지 않는다).
3. 브랜치 `"<prefix>#<이슈번호>"` 생성 → checkout
4. **Preflight 이월 변경 승격**: `HAS_STASH=true`였다면 미커밋 변경을 WIP 커밋으로 올려 워킹
   트리를 clean하게 만든다:
   `git add -A -- ':!.cure-implement' && (git diff --cached --quiet || git commit -m "wip: preflight carry-over")`
   - 이는 병렬 통합(cherry-pick)의 전제조건이다. 더티 워킹 트리 위에서 cherry-pick하면
     `error: your local changes would be overwritten`으로 실패하고, 병렬 워크트리에는 이 변경이
     없어 의미적 충돌이 통합 시점까지 감지되지 않는다.
   - 이 WIP 커밋은 배포 단계에서 최종 커밋에 squash되거나 정리된다.

> **중단 시 정리**: Phase 3부터는 이슈/브랜치가 존재하므로, 이후 단계가 실패하거나 사용자가
> 중단하면 이슈에 사유를 코멘트로 남기고 브랜치/이슈 삭제 여부를 확인한다.

## Phase 4: 코드 변경

### 사전 단계: 테스트 동결 (`[API]` 작업 대상)

`automation/freeze.md`를 읽고 아래 파라미터로 실행한다. **`[API]` 작업이 없으면 이 단계 전체를 스킵**한다.

| 파라미터 | 값 |
|---|---|
| 명세 | Phase 1에서 확정된 해당 작업의 변경 내용 |
| 작업 ID | 이슈 번호 |
| 동결 단위 | `[API]` 작업 1개 = 1 단위 (전 단위 완료 후 커밋·목록 기록 1회) |
| 참조 패턴 파일 | 동일·유사 도메인의 기존 테스트 1~2개 전문 |

동결은 **구현(병렬/순차) 시작 전에 완료**한다.

### 실행 모드

- **그룹 2개 이상** → 각 그룹을 에이전트로 병렬 실행. 통합 완료 전까지 메인 세션은 코드를 직접
  수정하지 않고 **cherry-pick 통합만** 담당한다.
- **그룹 1개** → 워크트리 없이 메인 세션에서 순차 실행.

### 병렬 실행

- **base**: 각 워크트리는 반드시 **현재 이슈 브랜치의 HEAD**에서 생성한다. 동결 커밋·WIP 커밋이
  HEAD에 포함돼야 재현·컴파일이 가능하다.
- **네이밍**: 워크트리 내 임시 브랜치 `wt/<이슈번호>-<그룹>`(예: `wt/52-A`). 임시 브랜치명에는
  `#`을 넣지 않는다 — 따옴표 방어가 필요한 표면을 줄인다.
- **에이전트 프롬프트에 포함할 것**: 그룹의 작업 상세, 타입별 절차 전문, 그룹 내부 순서,
  **커밋 소유권**(작업마다 워크트리 내 로컬 커밋 + 완료 보고에 **커밋 SHA 목록 순서대로 필수** —
  메인 세션이 cherry-pick 대상을 수집하는 유일한 경로), push·PR 금지.
- **Testcontainers 경합 방지**: N개 워크트리가 동시에 Docker 컨테이너를 띄우면 메모리·포트가
  경합한다. 병렬 에이전트는 **e2e(`pnpm test:e2e`)를 실행하지 않고** 구현 + `pnpm build && pnpm lint`
  + 단위 테스트(`pnpm test`)까지만 수행한다. e2e 실제 실행은 통합 후 메인 세션이 일괄 수행한다.
- **동결 목록**: 워크트리는 동결 커밋을 포함한 HEAD에서 생성되므로 상태 파일이 자동 포함된다.
  상대 경로로 기록돼 있어 워크트리 루트 기준으로 훅이 정상 매칭한다.
- **통합**: 모든 에이전트 완료 후 보고된 SHA를 **그룹 알파벳 순(A→B→C)**, 그룹 내부는 보고 순서로
  cherry-pick한다 (독립 그룹이라 이론상 순서 무관하지만 충돌 해결의 재현성을 위해 고정).
  통합 직후 `pnpm build && pnpm lint`로 통합 검증하고, 각 워크트리를 `git worktree remove` +
  임시 브랜치 삭제한다.

### `[API]` Test-First 구현 절차

1. 동결된 테스트·fixture를 읽고 기대하는 인터페이스와 동작을 파악한다
2. 명세 + 동결 테스트를 참조해 스텁 본문을 구현한다. 구현 중 새 시그니처가 필요해지면 테스트에
   맞춰 임의 생성하지 않는다 — 작업 명세와 스텁을 먼저 갱신하고 재파생·재동결한 뒤 재개한다
3. 테스트 실행 → 실패 시 **구현을 수정**해 재실행 (테스트는 동결 상태라 수정 불가)
4. 이의 제기는 `automation/freeze.md`의 「이의 제기(TEST-DISPUTE)」를 따른다
5. `pnpm build && pnpm lint`

### `[비API]` 일반 절차

1. 변경 적용 → `pnpm build && pnpm lint`
2. **기존 테스트 영향 검증**: 변경 대상을 의존하는 기존 테스트(전역 필터·인터셉터·가드·미들웨어
   변경 시 특히 주의)를 실행한다. 실패하면 테스트를 수정하되, **동결된 테스트에 영향이 가면
   수정하지 말고** TEST-DISPUTE에 준해 보고한다 (훅이 Edit/Write를 차단하므로 어차피 직접 수정
   불가). 영향받는 테스트가 없으면 스킵.
3. 변경 파일 재검토: 타입 오류, import 누락, 호환성, 보안 취약점

### 계약 이탈 감지 (모든 작업 공통)

구현 중 **Phase 1.5의 계약·보안 게이트에 해당하는 변경이 필요해지면 그 자리에서 중단**하고
사용자에게 보고한다. 임의로 진행하지 않는다 — 진단 단계에서 보이지 않던 계약 변경이 구현 중
드러난 것이므로, spec 승격 여부를 사람이 결정해야 한다.

> 이는 동결 테스트를 고치고 싶어질 때 TEST-DISPUTE로 멈추는 것과 같은 원리다 — **하네스는 스스로
> 경계를 넘지 않는다.** 이미 이슈·브랜치·동결 커밋이 존재하는 시점이므로, 승격을 택하면 그 브랜치를
> 유지한 채 spec을 작성하고 `/implement`로 이어받는다(이슈는 재사용).

## Phase 5: 통합 & 검토

1. 전체 변경사항 보고: 작업별 변경 파일, 테스트 결과 요약
2. **최종 검증**: `pnpm lint && pnpm test && pnpm test:e2e && pnpm build` 전부 green.
   병렬 통합이 있었으면 **e2e를 이 시점에 처음 일괄 실행**하는 것이므로 반드시 전 구간을 돈다.
   - **테스트 실패는 이 시점의 정상 경로다**: 병렬 에이전트는 자기 구현의 e2e GREEN을 확인한 적이
     없다. 실패 시 사용자에게 떠넘기고 멈추지 않는다 — **동결을 유지한 채 구현만 수정**하고
     재실행하는 루프를 GREEN까지 반복한다.
   - **루프 내 재실행은 실패분만 대상**으로 한다. 전부 GREEN이 된 뒤 최종 확인으로 전 구간 1회 재실행.
   - **서킷 브레이커**: 동일 테스트가 **3회 연속** 실패하면 루프를 멈추고 현황(실패 테스트, 시도한
     수정, 원인 분석)을 보고한 뒤 지시를 대기한다.
3. **동결 무결성 사후 감사**: 동결이 있었으면 `automation/freeze.md`의 「사후 감사」를 실행한다.
   감사는 항상 마지막 코드 변경 뒤에 오며, 이후 코드가 다시 바뀌면 재실행한다.
4. **환경변수 체크**: 새 환경변수가 도입됐으면 `automation/pipeline.md`의 「환경변수 추가 체크리스트」 확인
5. **사용자 확인 대기** — 추가 수정 요청 시 반복. OK 시에도 **동결은 아직 해제하지 않는다**
   (배포 실패로 재수정하는 시나리오에서 테스트가 무방비가 되지 않도록).

## Phase 6: 배포

`automation/ship.md`를 읽고 실행한다. 현재 이슈 브랜치에 있으므로 ship의 Preflight가 이를 감지해
**Phase 1·3을 스킵하고 Phase 2(검증)로 직행**한다. Phase 3에서 만든 WIP 커밋이 있으면 최종 커밋에
squash되도록 전달한다.

전달할 컨텍스트: 브랜치명, 타입, 이슈번호, Phase 5의 변경사항 요약, WIP 커밋 정리 방침.

`.cure-implement/preflight-stash.patch`가 있으면 삭제한다 (배포 성공 시점엔 작업이 이미 커밋·푸시
되어 잉여가 된다. 배포 실패 시에는 데이터 손실 방지 안전망으로 남겨둔다).

## 파괴적 DB 마이그레이션 2단계 배포

`automation/pipeline.md`의 「파괴적 DB 마이그레이션 2단계 배포 원칙」을 따른다.
Phase 1에서 해결책에 파괴적 마이그레이션이 포함되면 작업을 `[1차 배포]`(앱 코드에서 기존 스키마
참조 제거 + additive 마이그레이션)와 `[2차 배포]`(파괴적 마이그레이션)로 분리해 제시하고,
**이번 워크플로우에서는 `[1차 배포]` 작업만 실행**한다.

## 규칙

- 해결책 제시 시 코드 변경 없이 분석만 수행한다
- 사용자가 선택하지 않은 해결책은 절대 적용하지 않는다
- 하나의 해결책 안에서도 `[API]`/`[비API]` 작업을 반드시 분리해 제시한다
- `[API]` 테스트 실패 시 구현을 수정한다 — **기본 추정은 구현 결함, 입증 책임은 구현 쪽**
- 마이그레이션은 새 파일 추가만 — 적용된 파일 수정 금지. 전 테이블 `base-columns`
- 에러는 `ServiceException(ErrorCode)`만 사용. code 문자열 리터럴 금지
- Entity를 컨트롤러에서 직접 반환 금지 — mapper → Response DTO
- 상태 파일은 `.cure-implement/`(git-ignored)를 `/implement`와 공유한다. `git add -A`류 일괄
  스테이징에는 항상 `-- ':!.cure-implement'`를 붙인다
- 모든 `gh`/`git` 명령 실패 시 에러 내용을 사용자에게 보고한다
