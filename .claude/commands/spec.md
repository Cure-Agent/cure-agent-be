# /spec — 스펙 작성 하네스

`docs/specs/`에 다음 번호의 스펙 1편을 쓴다. **작성까지다** — [DOCS] 이슈·PR·배포는 `/ship`,
구현은 `/implement <번호>`의 몫이다.

## 모델

이 스킬이 로드된 턴은 frontmatter(`model: fable`, `effort: xhigh`)로 돈다. 오버라이드는 **그 턴까지**다 —
백그라운드 작업 통지나 새 프롬프트로 턴이 끊기면 세션 모델로 돌아오므로, 이어서 쓰려면 `/spec 계속`으로
다시 부른다. (AskUserQuestion 응답은 턴을 끊지 않는다 — 조사→질문→작성이 한 턴에서 이어지면 전부 이
설정으로 돈다.)

## Phase 0 — 대상·형식

1. 번호: `ls docs/specs/`의 최대 번호 + 1. **번호를 예약하지 않는다** (PR #82에서 중단한 관행).
2. `docs/specs/TEMPLATE.md`와 **직전 spec 1~2편 전문**을 읽는다 — 절 구성은 TEMPLATE이,
   문체·근거 밀도는 직전 spec이 기준이다.
3. 스펙이 §링크할 `docs/architecture.md` 섹션을 읽는다.

## Phase 1 — 실측 조사 (스펙의 모든 수치는 실측이다)

- 기대 수치(건수·번호·상태)는 **원본 데이터·프로덕션 기록·코드 현황을 직접 조회해 확정**하고,
  「실측 조사 (날짜, 표본)」 절에 표로 남긴다.
- 판정·추출 로직이 걸린 스펙이면 **그 로직을 스크립트로 모사해 산출까지 재현**한다 — spec 24는 이
  모사가 기대치 오류(145: 69→68)와 원문의 의도(권고 비도출)를 작성 단계에서 잡았다. 건너뛰었다면
  구현이 동결 테스트에 막혀 좌초했다.
- 추측으로 채우지 않는다 — 제목·발행일로 문서 계열을 추정하다 두 번 틀린 전례가 있다(§20 규범:
  "문서에서 관측한 패턴으로 판정한다").

## Phase 2 — 판단 확정

- 갈림길(처분·트레이드오프·범위)은 AskUserQuestion으로 확정하고, **결정과 그 근거를 spec 본문에
  남긴다** — spec은 작업 지시이므로 "왜 이 길인가"가 없으면 구현·리뷰가 같은 논쟁을 재연한다.
- 운영 부담을 늘리는 결정이면 그 교환이 왜 옳은지 명시한다 (spec 24 기준 10의 「의도적 부담」 서술).

## Phase 3 — 작성 규칙

- TEMPLATE.md 절 구성. **1페이지 유지**, architecture.md와 중복 서술 금지 — §링크로만 참조.
- **수용 기준은 동작 단위로 쪼갠다** — 한 항목에 동작이 둘이면(「A하고 B한다」·「A로 두되 B에 기록」)
  각각 단언 가능한 별도 기준이어야 한다. `automation/freeze.md` 「복합 기준」 규칙과 같은 이유:
  뭉치면 테스트 파생이 앞 동작만 단언한다(#120 사고 — 프로덕션까지 갔다).
- fixture 규약(원문이 아니라 **구조를 모방한 합성 텍스트**)과 Out of scope를 명시한다.
- 선행 spec의 규칙을 계승할 때는 「§NN 기준 N과 같은 이유」로 근거를 연결한다.

## Phase 4 — 마무리

- 사용자 확인 후 `/ship docs spec <번호> <제목>`으로 위임한다. 구현은 별도 `/implement <번호>`.
- **배포 범위는 `dev-only`다** — 스펙은 배포 산출물을 바꾸지 않으므로 dev 머지 + CI까지만 돌고 main 머지·프로덕션 CD는 돌지 않는다. 타입이 `[DOCS]`라 `/ship`이 기본값으로 잡지만(`automation/ship.md` Phase 1-3), 승인 문구의 「배포 범위」 줄로 한 번 더 확인한다. 스펙은 dev에 남아 **다음 `full` 배포에 함께 실린다** (`automation/pipeline.md` 「배포 범위」).
