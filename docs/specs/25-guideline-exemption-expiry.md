# 25. 면제·제외 목록의 만료 — fileHash 결합·만료 진단·통보

> **이 문서는 작성 시점의 작업 지시다 — 현재 시스템 상태가 아니다.**

## 목표

§23의 원문 결함 면제와 §24의 인제스트 대상 아님 목록은 `version`(release_date)을 만료 장치로 삼는다.
이 스텝은 그 장치의 구멍 둘을 막는다:

- **(A) 만료가 일어나면 진단이 거짓 방향을 가리키고, 아무도 능동적으로 모른다.** 개정판이 오면
  version 불일치로 항목이 그냥 「못 찾음」이 되어, 대상 아님 경로는 *"목록에도 없습니다"*(실제로는
  있다), 결함 면제 경로는 *"권고 번호 R20 중복"*(면제 만료인지 파서 회귀인지 구분 불가)이라고
  말한다. 지침 도메인은 `RealTimeAlertSender`를 쓰지 않아 잡 결과를 사람이 조회해야만 드러난다.
- **(B) 만료돼야 하는데 안 되는 경우 — 조용한 오적용.** 두 목록은 `release_date` **문자열**에만
  묶여 있다. NCKM이 같은 release_date로 파일만 교체하면(정오표 재발행) `source_documents`는
  해시 유니크라 새 행이 생기는데도 **면제·제외는 계속 적용된다** — 원문이 `【R20】` 중복을 고쳤어도
  여전히 면제하고, 새 중복이 생겨도 면제가 덮는다. 이슈 #106과 같은 성질의 조용한 판정이다.

(A)+(B)를 함께 다루기로 확정했다(2026-07-31 사용자 결정) — 두 문제가 같은 모듈·같은 조회 경로를
건드리므로 한 스텝이 자연스럽다.

## 실측 조사 (2026-07-31)

| 확인 항목 | 실측 |
|---|---|
| 만료 시 실패 메시지 | 대상 아님: `"…인제스트 대상 아님 목록에도 없습니다"` — 항목이 있는데 version만 다른 경우에도 같은 문구다. 결함 면제: §20 가드의 번호 열거뿐 — 만료 언급 없음 |
| 알림 배선 | `grep RealTimeAlertSender src/domain/guideline/` → 0건. `ObservabilityModule`은 `@Global`이고 sender를 export — **주입에 모듈 배선 변경 불요** |

### 해시 결합이 §24 e2e를 못 쓰게 만든다 — 주입점이 필요한 이유

§24의 e2e는 합성 본문(`%PDF-1.7\nDOC:90…`)으로 커밋된 항목에 매칭해 SKIPPED 경로를 검증한다.
fileHash가 판정 축이 되면 **합성 본문의 sha256이 커밋된 실물 해시와 같을 수 없으므로** 그 재현이
원리적으로 불가능해진다. 그래서 파이프라인·파싱의 목록 조회에 **주입 가능한 제공자**를 둔다 —
§3의 포트 기준(*"이걸 감싸지 않으면 수용 기준을 테스트로 동결할 수 없는가"*)을 정확히 충족하는
경우다. 기본값은 커밋된 목록이고, 순수 함수(`findNotIngestTarget`·`applyKnownSourceDefects`)는
그대로 남아 `verify:templates`가 **실물 PDF의 실제 해시**로 커밋된 상수를 직접 검증한다 —
e2e는 메커니즘을, CLI는 실제 항목을 덮는 분업이다.

## 범위 (진입점)

엔드포인트 없음.

| 진입점 | 변경 |
|---|---|
| `known-source-defects.ts` · `not-ingest-targets.ts` | 항목·identity에 `fileHash` 추가, **만료 후보 판별** 제공 |
| **목록 조회 주입점** (신규, 서비스 계층) | 두 목록의 조회를 감싸는 injectable — 기본값은 커밋된 상수, e2e가 치환한다 |
| `guideline-parse.service.ts` | 가드 실패 detail에 만료 후보 명시 + 만료 알림 |
| `guideline-pipeline.service.ts` | 마커 부재 FAILED detail에 만료 후보 명시 + 만료 알림, 판정 fileHash 결합 |
| `scripts/verify-templates.ts` | identity에 로컬 PDF sha256 포함 |
| §24 e2e 2편 | 목록 일치 시나리오를 주입 항목으로 유지 (단언은 그대로) |

- **항목 fileHash의 확정 원천은 프로덕션 `source_documents.file_hash`다.** 구현 시 로컬 표본
  해시와 대조해 채우고, 어긋나면 그 자체가 신호다(원격 파일이 이미 바뀌었다는 뜻). 어긋난 채
  배포되어도 **fail-closed**다 — 다음 잡이 만료 후보로 실패하며 알림이 나가고, 조용히 오적용되는
  방향으로는 절대 기울지 않는다.
- **이 스텝은 §24와 같은 방향으로 운영 부담을 늘린다.** 정오표 재발행마다 잡이 실패하고 사람이
  해시를 갱신해야 한다. 그 부담이 목적이다 — 원문이 바뀌었는데 면제·제외가 그대로 붙는 것은
  판정을 안 한 것과 같다.

## 수용 기준 (= 동결할 시나리오, Definition of Done)

> fixture는 §19·§20·§23 규약을 따른다 — 원문이 아니라 구조를 모방한 합성 텍스트다.

**만료 후보 판별 (두 목록 공통)**

1. `(sourceSystem, externalId)`는 일치하는데 `version`·`fileHash` 중 **하나라도** 다른 항목은
   판정에 적용되지 않는다
2. 그때 그 항목은 **「만료 후보」로 판별되어 호출자에 돌려진다** — 조용한 「못 찾음」과 구분된다
3. `version`이 같아도 `fileHash`가 다르면 1·2와 같다 — 같은 release_date 재발행이 만료를
   우회하지 못한다 (B의 핵심)
4. 네 축이 모두 일치할 때만 적용된다 — 적용 시 동작은 §23 기준 9~13·§24 기준 10~14 그대로다

**실패 진단이 만료를 가리킨다 (A-진단)**

5. 마커 없는 문서가 FAILED로 종결될 때 만료 후보가 있으면, detail에 **그 항목과 만료 축**
   (version 또는 fileHash, 기록값→현재값)이 담긴다 — "목록에도 없습니다"라는 거짓 안내가 사라진다
6. 결함 면제의 만료로 §20 가드가 실패할 때도 detail에 만료 후보가 담긴다 — 번호 열거만으로는
   면제 만료와 파서 회귀를 구분할 수 없다
7. 만료 후보가 없는 일반 실패의 detail은 기존 그대로다 — 만료 서술이 끼어들지 않는다

**만료 통보 (A-알림)**

8. 만료 후보가 판별되면 `RealTimeAlertSender`로 알림이 나간다 — 제목에 어느 목록·어느 문서,
   detail에 만료 축과 항목의 사유
9. 알림 발송 실패가 파이프라인 실행 결과를 바꾸지 않는다 (§15의 fire-and-forget과 같은 규칙)
10. 만료 후보가 없는 실패에는 알림이 나가지 않는다 — 만료는 「사람이 목록을 갱신해야 하는」
    신호이고, 일반 실패는 잡 기록의 몫이다

**fileHash의 원천과 CLI 정합**

11. 파이프라인·파싱 판정에 쓰는 fileHash는 §18이 **그 다운로드에 기록한 값과 같다**
    (`source_documents.file_hash`와 동일한 본문 해시)
12. `verify:templates`는 로컬 PDF의 sha256을 identity에 넣어 **같은 순수 함수로** 판정한다 —
    파이프라인과 CLI가 갈라지지 않는다 (§23·§24의 단일 모듈 참조 규칙)
13. 현재 항목 16건(결함 면제 1 + 대상 아님 15)에 실측 fileHash가 전문으로 채워진다
14. `pnpm verify:templates` 50건 대조가 **불일치 0을 유지**한다 — 해시 결합이 로컬 판정을
    하나도 바꾸지 않았다는 회귀 그물이다 (306은 여전히 면제로 `OK`, 대상 아님 15건은 `NOT_TARGET`)

**주입점과 §24 e2e 유지**

15. 목록 조회는 주입 가능한 제공자를 거친다 — 기본값은 커밋된 두 목록이고, e2e가 합성 본문의
    해시를 가진 항목으로 치환해 일치 경로를 재현한다 (위 「주입점이 필요한 이유」)
16. §24의 e2e 시나리오(목록 일치 → SKIPPED/PARSE, 사유 로그)는 주입 항목으로 **단언 그대로**
    유지된다 — 해시 결합이 §24의 수용 기준을 무효화하지 않는다

**e2e (신규)**

17. 잡에서 `(system, externalId, version)`은 일치하고 fileHash만 다른 문서 → `FAILED` +
    detail에 만료 명시 + 알림 1건 발송 (치환한 fake sender로 관측)
18. 네 축이 모두 일치하는 문서 → §24와 동일하게 `SKIPPED`, 알림 없음

## Out of scope

- **신규 미등재 문서 FAILED·잡 완료 요약의 알림** — 만료와 같은 「사람 행동 필요」 부류지만,
  잡 단위 통보는 개정 감지 스케줄러 spec이 잡 자동 실행과 함께 설계하는 것이 맞다
- **개정 감지 스케줄러** 자체 (별도 spec — §18부터의 예약)
- 면제·제외 목록의 DB화·관리 UI (§23과 같은 이유 — 리뷰 가시성)
- NCKM에 정정·재발행 요청 (코드 밖의 일)
- 알림 채널 추가·라우팅 변경 (§15 인프라 그대로 쓴다)
- 전건 재적재 실행 (배포 후 운영 판단)
