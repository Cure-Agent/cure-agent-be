# 39. refresh 세션 보존 정책 — 만료·회전분 파기 크론 편입

> **이 문서는 작성 시점의 작업 지시다 — 현재 시스템 상태가 아니다.** 시스템의 현재 모습은 architecture.md만이 서술한다.
> **1페이지 유지.** architecture.md와 중복 서술 금지 — §링크로만 참조한다.
> 수용 기준은 `/implement` Phase 2에서 테스트로 동결되며, 구현 중 수정할 수 없다.

## 목표

`auth_sessions` 행에 **수명을 준다**. 지금은 한 행도 지워진 적이 없고(실측 삭제 0건), 행을 만드는 것은
로그인이 아니라 **회전**이라 활성 사용에 비례해 무한히 는다(로그인 31회 → 99행). 그중에는 §36으로
개인정보를 파기한 **탈퇴 회원의 로그인 이력**이 그대로 남아 있다. 만료된 refresh 토큰은 어차피 교환이
거부되므로(`auth.service.ts:217`), 만료 후 유예가 지난 행을 §34 파기 크론의 **네 번째 축**으로 편입한다.

## 판단 근거 (2026-08-05 사용자 확정)

| 쟁점 | 판단 |
|---|---|
| 유예 기산점 | **`expires_at` 단일 기준.** 실측상 `rotated_at`·`revoked_at`이 `expires_at`보다 뒤인 행이 **0건**이라 만료가 항상 마지막 사건이고, NOT NULL이며 행 생성 후 불변이라 판정이 **한 컬럼으로 닫힌다**. 만료 후 토큰은 교환이 거부되므로 남은 가치는 재사용 감지 알림뿐 — 즉 **30일 유예가 곧 탈취 감지 꼬리의 길이다** |
| 상태별로 기산점을 나누지 않는 이유 | 폐기·회전분을 `revoked_at`·`rotated_at` 기준으로 더 일찍 지우면 조건이 셋으로 늘고 **감지 꼬리가 상태마다 달라진다**. 로그아웃한 세션의 구 토큰이 재사용돼도 그것은 탈취 신호이므로(`auth.service.ts:206` — `rotatedAt \|\| revokedAt`을 같이 본다) 꼬리를 짧게 할 이유가 없다 |
| `created_at` 기준이 아닌 이유 | `AUTH_REFRESH_TTL_DAYS`를 늘리면 **살아 있는 세션이 삭제 대상이 된다.** `expires_at`은 행마다 발급 시점의 TTL을 이미 담고 있어 설정 변경과 무관하다 — 유예와 TTL이 암묵적으로 결합하지 않는다 |
| 재사용 감지 행을 보존하는가 | **지운다.** 프로덕션 감지 2건이 **전부 회전 67ms·83ms 뒤**에 찍힌 **동시 refresh 경합**(더블 서브밋)이라 침해 증거가 아니다. 예외를 두면 오탐만 영구 축적된다. 침해 사실 자체는 `AUTH_REFRESH_REUSED` 알림(§14)과 메트릭에 이미 남으므로, 이 행이 유일한 기록도 아니다 |
| 유예를 임상 데이터와 공유하는가 | **분리한다.** §34가 `DATA_PURGE_RETENTION_DAYS`를 파라미터로 둔 이유는 「법정 보존 대상인지의 판단이 뒤집힐 수 있어서」인데, 뒤집히면 그 값은 **위로만 움직인다**(예: 3650일). 공유하면 refresh 토큰 해시가 10년 남는다 — 두 값은 근거가 다르므로 함께 움직여선 안 된다 |
| 탈퇴 시 즉시 삭제하지 않는 이유 | §36은 세션을 **폐기하되 삭제하지 않는다.** 즉시 삭제로 바꾸면 탈퇴 직후의 구 토큰 재사용이 감지 대신 401로 흘러 §4.3 신호를 잃는다. 만료 기준이면 **최대 44일** 뒤 사라지므로 파기 의무도 유한한 기간 안에 이행된다 |
| 인덱스를 만드는가 | **만들지 않는다** — §12 「측정 후 도입」 그대로다. 정상 상태 상한이 484행이라 전수 스캔이 무의미하게 싸다(§12는 9,727행 전수 스캔 ~1s도 감수했다). §34가 부분 인덱스를 둔 것은 **삭제분이 소수라 인덱스가 작아서**인데, `expires_at`은 100% 행에 있어 그 논리가 성립하지 않는다 |

## 실측 조사 (2026-08-05, 프로덕션 DB + 코드)

| 확인 항목 | 실측 |
|---|---|
| `auth_sessions` | **99행** — 폐기 61 · 회전 68 · 재사용 감지 2 · 살아 있는 것 9 · 의료인 6 · family 31 |
| **만료된 행** | **0건** — 가장 이른 만료가 **2026-08-10**이다 |
| 행을 만드는 것 | 로그인 31회 → **99행(로그인당 3.19)**. 최다 family는 **34.1시간에 23행** — 증가는 로그인이 아니라 **회전**이 이끈다 |
| **지금까지 삭제된 세션** | **0건** — 유일한 삭제 경로(§36 클리닉 파기 ④)의 조건인 파기된 클리닉이 **0개**다 |
| 일평균 생성 | **11.0건** (99행 / 9일, 2026-07-27~08-04) |
| 데이터 나이 | 전 테이블 `min(created_at)`이 **2026-07-27 16:37:20으로 동일** — 잘린 적 없는 전건이다 |
| `expires_at` | NOT NULL · `created_at + 14일`과 **오차 41ms 이내** · 그보다 뒤인 `rotated_at`·`revoked_at` **0건** |
| **tombstone 회원의 세션** | **2명 6행** — 2026-08-04 탈퇴, 최초 세션 2026-07-27. **개인정보를 파기한 사람의 로그인 이력이 남아 있다** |
| 재사용 감지 2건 | 회전 **0.083초 · 0.067초** 뒤 — 동시 요청 경합이지 탈취가 아니다 |
| **참조 FK** | **0개** — `auth_sessions`를 가리키는 테이블이 없다(잎). §34가 씨름한 3~5단 역순 삭제가 **없다** |
| 테이블 크기 | 96 kB(heap 32 kB) · 인덱스는 `pkey`·`idx_auth_sessions_family` 둘 |
| 유예 30일 적용 시 | 첫 삭제 **2026-09-09에 11행**, 이후 일 3~24행. 정상 상태 상한 **≈484행**(수명 44일 × 11.0) |

두 행이 이 스펙을 결정한다. **⑴ 만료된 행이 0건이다** — 배포해도 당장은 아무것도 지우지 않고 첫 삭제는
2026-09-09이다. 이 스펙은 적체를 치우는 것이 아니라 **수명을 유한하게 만드는 예방 조치**이며, 그래서
수용 기준은 프로덕션 표본이 아니라 **합성 fixture로만** 세울 수 있다. **⑵ 탈퇴 회원 6행이 남아 있다** —
§36이 개인정보 네 필드를 익명화했는데 그 사람이 언제 몇 번 로그인했는지는 그대로다. 무한 증가보다
이쪽이 **지금 실재하는 결함**이다.

## 수용 기준 (= 동결할 시나리오, Definition of Done)

**유예 경과분만 지운다**

1. 만료 후 유예가 지난 세션이 `purge()`로 **물리 삭제된다** (e2e — DB 직접 조회, 잔존 0)
2. 만료됐지만 **유예 미경과** 세션은 남는다 (e2e — 양성 대조군)
3. 아직 만료되지 않은 **살아 있는** 세션은 남는다 (e2e)
4. 파기된 세션의 소유자 `clinicians` 행은 **남는다** (e2e — 세션 파기는 계정 파기가 아니다)
5. `purge()` 반환값의 `sessions`가 **실제로 지운 수**와 같다 (유닛)

**만료 하나로만 판정한다**

6. `revoked_at`이 찍힌 세션도 만료+유예 전에는 **남는다** (e2e — 로그아웃이 파기를 앞당기지 않는다)
7. `rotated_at`이 찍힌 세션도 만료+유예 전에는 **남는다** (e2e)
8. `reuse_detected_at`이 찍힌 세션이 유예 경과 시 **함께 지워진다** (e2e — 예외를 두지 않기로 한 판단의 직접 단언)

**유예 = 재사용 감지 꼬리**

9. 유예 미경과 회전분의 **구 refresh 쿠키**로 `POST /auth/refresh` → **401 `AUTH_REFRESH_REUSED`** (e2e)
10. 그 요청이 해당 family의 살아 있는 세션을 **전부 폐기한다** (e2e — 감지가 유예 동안 살아 있다)
11. 유예 경과로 파기된 뒤 **같은 구 쿠키**로 `POST /auth/refresh` → **401 `UNAUTHORIZED`** (e2e —
    감지 신호 상실이 이 스펙이 **감수하는 손실**이다. 거부 자체는 유지된다)

**탈퇴·강퇴 회원**

12. 탈퇴(tombstone) 회원의 세션도 만료+유예 경과 시 **지워진다** (e2e)
13. 탈퇴만으로는 세션 행이 **사라지지 않는다** (e2e — §36 revoke 계약 불변)
14. 무소속(강퇴, §38) 회원의 세션도 **같은 규칙으로** 지워진다 (e2e)

**두 유예 축의 분리**

15. `DATA_PURGE_SESSION_RETENTION_DAYS`만 바꾸면 세션 파기 시점이 **바뀐다** (유닛 — 주입 시각)
16. `DATA_PURGE_RETENTION_DAYS`를 바꿔도 세션 판정은 **변하지 않는다** (유닛 — 축 분리의 직접 단언)
17. `DATA_PURGE_SESSION_RETENTION_DAYS` 기본값이 **30**이다 (유닛)

**기존 크론 계약 회귀**

18. 배치 상한을 넘는 세션은 **다음 틱으로 남는다** (유닛)
19. 그 남긴 수가 `deferred`에 **포함된다** (유닛 — 조용한 절단 금지, §34 기준 21)
20. 락 획득 실패면 세션 **대상 산출조차 하지 않는다** (유닛 — fail-closed, §34 기준 20)
21. 락 미획득 시 `data_purge_total{target=session,outcome=skipped}`가 오른다 (유닛)
22. 파기 성공 시 `{target=session,outcome=purged}`가 **지운 수만큼** 오른다 (유닛)
23. 파기 중 예외 시 `{target=session,outcome=failed}`가 오른다 (유닛)
24. 세션 축이 추가돼도 같은 틱의 **대화·환자 파기 결과가 변하지 않는다** (e2e — §34 회귀)
25. 클리닉 파기(§36 ④)가 그 구성원의 세션을 **만료 여부와 무관하게** 지우는 동작이 유지된다
    (e2e — 두 삭제 경로가 공존하며, 새 축이 옛 축을 대체하지 않는다)

fixture 규약: 유예 경과 세션은 프로덕션 행을 복사하지 않고 **실제 로그인으로 만든 뒤 `expires_at`을
과거로 UPDATE해 합성한다**(§34 `markConversationPastRetention` 선례). 회전분은 `POST /auth/refresh`를
**실제로 호출해** 만들고 `rotated_at`을 직접 찍지 않는다 — 직접 찍으면 구 쿠키 원문이 없어 기준 9·11의
replay를 세울 수 없다. 재사용 감지 행(기준 8)도 **구 쿠키를 실제로 재제출해** 만든다. 무소속 회원(기준
14)은 §38 강퇴 경로를 타고, `refresh_token_hash`는 발급된 실값을 쓴다.

## Out of scope

- **세션 목록·개별 폐기 API**(「내 기기 관리」) — 보존 정책과 직교하며 화면·DTO가 딸린다. 이 스펙은
  서버가 스스로 지우는 규칙만 정한다
- **로그인 이력의 감사 테이블 이관** — 파기 전에 별도 테이블로 옮기는 안. 남길 실익이 판단되지 않았고,
  남긴다면 **그것이 새로운 무한 증가 테이블**이 되어 같은 문제를 한 칸 옮기는 데 그친다
- **탈퇴 즉시 세션 물리 삭제** — §36의 revoke 계약을 바꾸는 변경이고, 위 판단대로 탈퇴 직후의 감지
  신호를 잃는다. 만료 기준으로도 최대 44일 안에 파기된다
- **재사용 감지 이력의 장기 보관·SIEM 연동** — 표본 2건이 전부 경합 오탐이라 지금 설계하면 **오탐
  창고**를 만든다. 실제 탈취가 관측된 뒤 판단한다
- **동시 refresh 경합의 오탐 자체를 없애는 것**(짧은 grace window 허용) — 실측 2건이 그 결함을 가리키지만
  이는 §4.3 **감지 로직**의 문제이지 보존 정책이 아니다. 고치려면 재사용 판정에 시간 창을 넣어야 하고
  그것은 탈취 탐지 민감도를 낮추는 별도 판단이다
- **`pipeline_runs` 등 다른 증가 테이블** — 실측 716행. 지침 인제스트 계열이라 기산점도 보존 근거도 다르다
- **`AUTH_REFRESH_TTL_DAYS`(14일) 조정** — 이 스펙은 TTL을 상수로 받아들이고 **그 뒤의 꼬리만** 정한다
- **`PurgeOutcome.clinics` 누락 보정** — §36이 클리닉 축을 반환값에 넣지 않은 것은 이 스펙 이전의 상태이고,
  함께 고치면 세션과 무관한 유닛이 같이 흔들린다
