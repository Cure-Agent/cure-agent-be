# 41. 데모 온보딩 — 가상 환자 시딩 + 빈 대화 예시 질의문

> **이 문서는 작성 시점의 작업 지시다 — 현재 시스템 상태가 아니다.** 시스템의 현재 모습은 architecture.md만이 서술한다.
> **1페이지 유지.** architecture.md와 중복 서술 금지 — §링크로만 참조한다.
> 수용 기준은 `/implement` Phase 2에서 테스트로 동결되며, 구현 중 수정할 수 없다.

## 목표

라이브 데모에 처음 들어온 사람이 **직접 만들지 않아도 환자가 있고, 직접 짜내지 않아도 물어볼 질문이
있게** 한다. 지금 가입을 마치면 환자 0명 · 대화 0개 · 빈 입력창이 전부다 — §5.6의 「환자 맞춤 대화」는
환자를 먼저 등록해야 도달하고, §5.3의 지침 질의는 무엇을 물어야 할지를 사용자가 알고 있다고 전제한다.
이 스텝은 클리닉 개설 트랜잭션에 가상 환자 3건을 싣고, 메시지가 0건인 대화에 **답할 수 있다고 확인된**
예시 질의문을 입력창 위에 띄운다.

새 판단을 만들지 않는다. 환자 등록·대화 생성·질의 경로는 §9·§5.3·§5.6 그대로이고, 이 스텝이 더하는
것은 **그 경로의 첫 입력을 미리 채워두는 것**뿐이다.

## 실측 조사 (2026-08-29, 프로덕션 DB + 평가셋 + 컷 스윕 원자료)

| 확인 항목 | 실측 |
|---|---|
| 클리닉 | **3개** — 환자가 있는 곳은 **1개뿐**(5명). 나머지 2개는 환자 0 · 대화 0/1 |
| 대화 (전체·삭제 포함) | GUIDELINE_QA **43**(삭제 42) · PATIENT_GUIDANCE **10**(삭제 5). 살아남은 GUIDELINE_QA 1건은 **메시지가 0건**이다 |
| USER 메시지 | **63건** — 고유 문장 **46개**. 길이 min 2 · avg 25 · max 78자, **80자 이상 0건** |
| **입력창 placeholder를 그대로 친 횟수** | **9건 / 63** — `chat-panel.tsx`의 예시 문구("만성 요통에 침 치료가 효과적인가요?")가 그대로 질문으로 제출됐다 |
| ASSISTANT 결말 | ABSTAINED **35** · COMPLETED 21 · FAILED 6 · STREAMING 1 → **기권 56%** |
| COMPLETED의 인용 | 21건 중 **19건**에 인용이 붙었다 — 답이 나오기만 하면 근거는 붙는다 |
| 질문 길이대별 기권률 | <30자 25/46(54%) · 30–49자 8/11(73%) · 50자+ 2/6(33%) |
| 데모 3진단의 ACTIVE 청크 | 골다공증 **51** · 주의력결핍 과잉행동장애 **194** · 류마티스 관절염 **53** (전체 ACTIVE 7,154 / 63 버전) |
| 일반 질의문 3주제의 ACTIVE 청크 | 만성 요통 증후군 **70** · 불면장애 **157** · 편두통 **130** |
| 환자별 질의문 3개의 출처 | `evalgen-answerable-015`·`-014`·`-114` — 전부 `answerable/approved` **원문 일치** |
| 그 3문항의 컷 스윕 결과 | 2026-08-25 run1·run2 **양쪽 모두** 과잉 기권·Recall@5 실패 목록에 **없음**(운영 컷 9) |
| 일반 질의문 3개의 출처 | `-059`·`-016`·`-036` 계열을 **다듬은 문장** — 원문 일치 아님. 답변가능성 **미실측** |

두 행이 이 스펙을 결정한다. **⑴ placeholder 9건이다.** 사람들은 눈앞에 놓인 예시를 그대로 친다 —
이 제품에서 이미 관측된 사실이므로, 좋은 예시를 놓는 개입은 「쓰일 것 같다」가 아니라 **쓰인다**.
**⑵ 기권 56%다.** 그런데 길이대별 기권률이 54→73→33%로 흩어져 **길이가 원인이 아니다.** 실제 질문
46개는 「비염은 어떻게 치료하는게 좋을까?」처럼 지침의 권고 단위와 결이 다르고, 평가셋에서 승인된
문항은 그 권고를 겨냥해 역생성된 것들이다. 그래서 개입은 「길게 쓰게 하기」가 아니라 **승인 문항을
그대로 놓기**다.

가상 환자 3건의 전체 값 — **기준 4·5·8~13이 단언하는 대상**이다. 비운 칸은 넣지 않는다(`waistCm`·
`clinicalNotes` 일부). `birthYear`는 상수이며 2026년 기준 각각 72·11·64세로 읽힌다:

## 판단 근거 (2026-08-28~29 사용자 확정)

| 쟁점 | 판단 |
|---|---|
| 환자를 **어떻게** 넣는가 | **클리닉 개설 트랜잭션에서 시딩한다.** 로그인이 소셜 전용이라 공용 데모 계정을 나눠 줄 수 없고, 초대 링크는 §35가 **1회용 + 7일 만료**로 못 박아 상시 진입점이 못 된다. 남는 경로는 「가입한 사람의 클리닉에 넣는다」 하나다. 빈 목록에 「불러오기」 버튼을 두는 안은 BE 변경이 0이지만 클릭이 하나 늘고, 데모의 목적이 **클릭을 줄이는 것**이다 |
| 합류 경로에도 넣는가 | **넣지 않는다.** 초대 합류자는 **이미 환자가 있는** 클리닉으로 들어가므로(§35 clinic 스코프 공유) 거기서 또 시딩하면 동료의 실제 목록에 가상 환자가 섞인다. 시더는 `clinicName` 분기에만 둔다 |
| 기본값 | **꺼짐. 정확히 `'true'`만 켠다.** 다른 불리언 env(`LLM_ANSWERABILITY_GATE_ENABLED`)는 `!== 'false'`로 기본 켜짐인데 **방향이 반대다** — §09 기준 2(커서 페이지네이션) 동결 테스트가 새 클리닉에 환자 3건을 만들고 2+1 페이지를 단언하므로, 기본 켜짐이면 그 단언이 6건을 본다. 「동결을 깨지 않는 기본값」이 이 플래그의 존재 이유이고, 켜는 자리는 배포 환경뿐이다 |
| 시더를 어느 모듈에 두는가 | **컨트롤러 없는 `DemoPatientSeedModule`.** AuthModule이 PatientModule을 import하면 `PatientController`가 AuthModule 하위로 스캔돼 **생성되는 OpenAPI의 path 순서가 통째로 바뀐다**(실측: 814줄 재정렬 diff). 동작은 같지만 계약 파일이 흔들리면 §1의 「커밋된 스펙 = 재생성본」 검사가 리뷰어에게 무의미해진다. 시딩은 스코프 질의가 아니라 고정 픽스처 삽입이라 `PatientRepository`를 우회하는 대가가 없다 |
| 생년을 상수로 두는가 | **상수로 둔다**(2026년 기준 72·11·64세 역산 = 1954·2015·1962). 응답의 `age`는 「올해 − 생년」 파생이라 해가 바뀌면 데모 환자도 늙는다. 시딩 연도에서 역산하면 고정되지만, **이 데모의 예상 수명 안에서는 드리프트가 문제되지 않는다**는 판단으로 읽기 쉬운 쪽을 택했다. 대신 **수용 기준에서 나이를 단언하지 않는다** — 기대값이 해마다 밀려 새해 첫날 코드 변경 없이 스위트가 깨진다 |
| 질의문을 무엇으로 고르는가 | **케이스 라벨이 아니라 진단명.** 라벨은 사용자가 바꿀 수 있는 자유 문자열이고, 진단명은 그 환자에게 무엇을 물을 수 있는지를 실제로 결정한다. 부분일치로 찾으므로(「폐경 후 원발성 골다공증」·「소아 ADHD 의심」) 데모 환자뿐 아니라 **같은 진단으로 직접 등록한 환자**에게도 걸린다 |
| 화면이 환자를 어떻게 아는가 | **`ConversationSummaryResponseDto`에 `patientId` additive 노출.** 컬럼은 스키마에 이미 있고, §5.3의 「기존 대화 조회」도 이미 계약에 있다. `?conversation={id}`로 바로 들어온 화면이 환자 프로필을 되찾는 축은 이것뿐이다 — 제목의 `CASE-` 라벨을 파싱하는 안은 BE 변경이 0이지만 사용자가 대화명을 바꾸면 끊긴다. GUIDELINE_QA는 null이라 필드가 응답에서 빠지므로 기존 소비자의 형태가 유지된다 |
| 환자별 문구를 고정하는가 | **평가셋 승인 원문으로 고정한다.** 환자 맞춤 대화는 기권하면 **데모가 그 자리에서 깨진다** — 프로필까지 합성해 던진 질문이 「근거를 못 찾았다」로 끝나면 보여줄 것이 없다. 세 문항 전부 컷 스윕 2회에서 과잉 기권 목록에 없었으므로 그 이력이 유일한 담보이고, 문구를 고치면 담보가 끊긴다 |
| 일반 문구는 다듬는가 | **다듬은 문장을 유지한다 — 답변가능성은 미실측이다.** 일반 대화는 기권해도 **다른 질문을 다시 던지면 되는 자리**라 손실이 작고, 승인 원문은 「귀비탕가감을 고려할 수 있나요?」처럼 시험문제 톤이라 첫 화면에 놓기에 읽히지 않는다. 이 교환을 명시적으로 기록한다 — 데모에서 일반 질의문이 기권하면 **문구가 아니라 이 판단을 다시 본다** |
| 언제 사라지는가 | **메시지가 1건이라도 생기면 사라진다.** 입력창 위 자리는 대화가 시작되면 방금 받은 답변이 차지해야 하고, 예시가 남으면 다음 질문을 가린다. 두 번째 예시를 쓰려면 새 대화를 만들어야 하지만, 데모 동선은 「새 대화 → 예시 클릭 → 답변」 한 바퀴로 충분하다 |
| 클릭이 곧 전송인가 | **아니다 — 입력창을 채우기만 한다.** 클릭 한 번이 LLM 호출이면 실수로 눌렀을 때 되돌릴 수 없고, 예시를 자기 환자에 맞게 고쳐 던지는 흐름이 막힌다. 커서를 문장 끝에 두는 것까지가 「채운다」의 완성이다 |

## 수용 기준 (= 동결할 시나리오, Definition of Done)

**시딩은 플래그가 켜졌을 때만, 개설 분기에서만 일어난다**

1. `DEMO_SEED_ENABLED`가 꺼져 있으면 클리닉 개설이 `patients`에 **한 행도 쓰지 않는다** (유닛)
2. env가 미지정·빈 값이면 **꺼진 상태다** (유닛 — 기본값의 직접 단언)
3. env가 `'true'` 외의 값이면(`'1'`·`'yes'` 등) **꺼진 상태다** (유닛 — 다른 킬스위치의 `!== 'false'`와 방향이 반대임의 직접 단언)
4. 켜진 상태로 클리닉을 개설하면 목록에 환자 **3건**이 보인다 (e2e)
5. 그 순서가 **CASE-001 → CASE-002 → CASE-003**이다 (e2e — `id DESC` 목록에서 라벨 순으로 읽히게 한 판단)
6. 초대로 합류한 구성원의 목록에도 그 **3건뿐**이다 (e2e — 합류가 두 번째 배치를 만들지 않는다)
7. 시딩된 환자는 요청한 클리닉에만 속한다 (유닛 — `clinicId` 전건 일치)

**시딩된 환자는 일반 등록 환자와 구분되지 않는다**

8. 상세 조회가 진단·투약·알레르기를 **평문 배열로** 돌려준다 (e2e — 복호화 경로가 같다)
9. 임상 메모가 있는 환자(CASE-002)는 그 문자열을 그대로 돌려준다 (e2e)
10. 임상 메모가 없는 환자는 `clinical_notes_encrypted`가 **null이다** (e2e — 빈 문자열을 암호화해 채우지 않는다)
11. `diagnoses_encrypted`가 `v1.` 접두 암호문이고 진단명 평문을 **포함하지 않는다** (e2e — §4.5)
12. 상세의 `birthYear`·`sex`가 위 픽스처 표의 값과 같다 — CASE-001 `1954`/`FEMALE`, CASE-002 `2015`/`MALE`,
    CASE-003 `1962`/`FEMALE` (e2e — **`age`는 단언하지 않는다**: 파생값이라 해마다 밀린다)
13. 신장·체중이 실려 `bmi`가 계산된다 (e2e — 목록 행이 빈 칸으로 보이지 않는다)

**계약은 한 필드만 는다**

14. PATIENT_GUIDANCE 대화의 상세 응답에 `patientId`가 실린다 (e2e)
15. GUIDELINE_QA 대화의 응답에는 `patientId` **키 자체가 없다** (e2e — 기존 소비자 형태 유지)
16. `pnpm openapi:export` 재생성본이 커밋된 스펙과 **같다** (기존 contract 테스트 — 회귀)

**예시 질의문은 빈 대화에만 뜬다**

17. 메시지 0건인 GUIDELINE_QA 대화에 일반 질의문 **3개**가 입력창 위에 뜬다 (유닛)
18. 메시지가 1건이라도 있으면 **뜨지 않는다** (유닛)
19. 질문을 전송하면 그 즉시 **사라진다** (유닛 — 서버 목록 갱신을 기다리지 않는다)

**환자 맞춤은 진단으로 고른다**

20. 진단이 걸리는 환자 맞춤 대화에는 그 질의문 **하나만** 뜬다 (유닛)
21. 그 대화에 일반 질의문은 **함께 뜨지 않는다** (유닛)
22. 진단명은 **부분일치**로 찾는다 — 「폐경 후 원발성 골다공증」·「소아 ADHD 의심」이 걸린다 (유닛)
23. 진단이 여러 개면 그중 하나만 걸려도 찾는다 (유닛)
24. 걸리는 진단이 없으면 **일반 질의문으로 떨어진다** (유닛 — 빈 자리를 남기지 않는다)
25. 환자 프로필을 아직 못 받은 동안은 **아무것도 뜨지 않는다** (유닛 — 일반→환자 교체로 손 밑에서 항목이 바뀌지 않게)
26. 환자 조회가 실패해도(삭제된 환자 등) 일반 질의문으로 떨어진다 (유닛)

**클릭은 전송이 아니다**

27. 예시를 누르면 입력창 값이 그 문장이 된다 (유닛)
28. 그 클릭이 스트림을 **호출하지 않는다** (유닛 — 고쳐 던질 수 있어야 한다)

**환자별 질의문의 출처를 잠근다** — 두 레포로 갈라진 사실이라 각 레포에서 절반씩 단언한다

29. `evalgen-answerable-015`·`-014`·`-114`가 평가셋에 **`answerable`·`approved`로 여전히 존재하고**
    그 `question`이 위 실측표에 적힌 문자열과 같다 (BE 유닛 — 출처가 사라지거나 바뀌면 담보가 끊긴다)
30. FE의 환자별 질의문 3개가 그 세 문자열과 **자구까지 같다** (FE 유닛 — 문구 드리프트 차단.
    기대값은 기준 29가 지키는 원문에서 옮긴다. **일반 3개에는 이 기준을 걸지 않는다**)

fixture 규약: **기준 4~13의 기대값 원천은 위 「가상 환자 3건의 전체 값」 표다** — 테스트는 그 표를
그대로 옮겨 단언하며, 구현의 픽스처 파일을 읽어 기대값을 만들지 않는다(그러면 오라클이 구현을
따라가 무엇도 검증하지 못한다). e2e는 실 LLM·실 코퍼스를 부르지 않는다. 시딩은 **실제 가입 API**(`socialSignUp`)를
지나 검증하고 DB를 직접 조작하지 않는다 — 시더가 가입 트랜잭션에 합류하는지가 기준 4~7의 대상이기
때문이다(§39 「회전분은 실제로 refresh를 호출해 만든다」와 같은 이유). 합류자(기준 6)는 §35 초대
발급·소비 경로를 그대로 탄다. 플래그는 env가 아니라 **설정 프로바이더 override**로 켠다 — env는
모듈 초기화 때 한 번만 읽혀 나중 변경이 반영되지 않고, 다른 스위트로 값이 샌다.

## Out of scope

- **일반 질의문 3개의 답변가능성 실측** — 위 판단표대로 가독성을 택하며 미실측을 감수한다. 재검토
  트리거는 「데모에서 일반 질의문이 기권했다」이고, 그때 고칠 것은 문구가 아니라 그 판단이다
- **기존 클리닉 소급 시딩** — 프로덕션 3개 중 2개가 환자 0이지만 전부 개발자 본인 계정이고, 소급은
  「이미 쓰던 클리닉에 가상 데이터를 넣는다」라 시딩을 개설 분기로 제한한 판단과 정면으로 어긋난다
- **데모 환자 표식(배지·`isDemo` 컬럼)** — 일반 등록 환자와 구분되지 않는 것이 기준 8~13의 의도다.
  구분이 필요해지는 시점은 「사용자가 데모 환자를 지우고 싶다」인데, §34 삭제가 이미 그 경로다
- **예시 질의문을 접었다 펴는 패널** — 두 번째 예시를 같은 대화에서 쓰게 하는 안. UI 상태가 하나
  늘고 수용 기준도 는다. 데모 한 바퀴에는 새 대화가 값싸다
- **BE가 질의문을 서빙하는 엔드포인트**(`GET /conversations/{id}/suggested-prompts`) — 단일 출처이고
  `patientId`를 노출하지 않아도 되지만, 스펙·계약 표면·동결 e2e가 따라붙는다. 질의문은 화면 콘텐츠라
  FE 상수로 충분하고, `patientId`는 그 자체로 §9가 이미 가진 사실이다
- **placeholder 문구 정리** — 실측 9건이 그대로 제출된 문장이 아직 `chat-panel.tsx`에 남아 있다.
  예시 질의문이 그 역할을 대신하므로 지울 후보지만, 예시가 안 뜨는 대화(메시지 1건 이상)에서는
  placeholder가 유일한 힌트라 함께 판단해야 한다
- **환자 프로필 편집 폼의 생년·성별 칸** — 시딩은 두 값을 넣지만 `patient-detail-panel.tsx`의 「프로필
  수정」에는 두 칸이 없어 화면에서 고칠 수 없다(§09 이전 상태). 이 스펙이 만든 결함이 아니다
- **다국어·i18n** — 질의문·라벨이 전부 한국어 상수다. 제품 전체가 그렇다
