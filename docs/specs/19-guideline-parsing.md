# 19. 지침 PDF 파싱·청킹

## 목표

§18이 수집한 지침 PDF를 **권고문 단위 청크**로 분해해 `GuidelineIngestInput`(§5 계약)을 생성한다.
생성된 JSON은 기존 `GuidelineIngestService`가 그대로 적재하므로 **인제스트 계약은 건드리지 않는다**.

핵심 설계는 **텍스트 추출과 청킹의 분리**다. 추출은 라이브러리 래퍼(부수효과)이고, 청킹은
`(pages: string[], meta) → GuidelineIngestInput`인 **순수 함수**다. 청킹이 이 스텝의 실질 가치이며,
순수 함수라 5.6MB PDF 없이 텍스트 fixture만으로 전량 검증할 수 있다.

> **fixture는 지침 원문이 아니라 구조를 모방한 합성 텍스트로 만든다.** 레포에는 임베딩만 두고
> 원문은 NCKM 링크로 참조한다는 방침(§18)이 테스트 fixture에도 적용된다 — 실제 페이지를 커밋하면
> 그것이 곧 원문 일부의 재배포다. 검증 대상은 **구조**(블록 마커·등급 표기·헤더 계층·페이지 번호)이므로
> 합성 텍스트로 충분하며, 실제 PDF에 대한 확인은 `.cure-data/`의 골든 파일로 CLI를 수동 실행해 수행한다.

## 범위 (진입점)

엔드포인트 없음 — CLI 배치다.

| 진입점 | 동작 |
|---|---|
| `pnpm parse:nckm <pdf> --guide-idx <idx> [--out <json>]` | PDF → 페이지 텍스트 → 권고문 청킹 → `GuidelineIngestInput` JSON |

- 출력 JSON은 기존 `pnpm ingest <json>`이 소비한다. **파싱과 적재를 한 명령으로 합치지 않는다** —
  중간 산출물을 눈으로 검토하는 단계가 인용 정확도의 마지막 방어선이다.
- 신규 의존성: `unpdf`(pdfjs 기반, 한글 추출 실측 확인). 외부 HTTP가 아니라 로컬 라이브러리이므로
  §3 포트 기준에 해당하지 않는다 — 골든 텍스트로 실물 검증한다. **번들 pdfjs에 `keepWhiteSpace` 패치를
  건다**(`patches/unpdf@1.8.0.patch`, #535 개정) — 줄 끝 공백 글리프를 살리기 위해서다. 패치 방식과
  업그레이드 주의는 「어절 경계 줄바꿈」 참조.

### 문서 메타의 출처

PDF 텍스트에는 발행처·발행일이 없다(뒷표지에 ISBN뿐). 따라서 `GuidelineIngestInput`의 문서 메타는
**§18이 이미 적재한 `source_documents`에서 읽는다** — `--guide-idx`로 최신 행을 조회한다.

| 필드 | 출처 | 비고 |
|---|---|---|
| `title` / `publisher` | `source_documents.title` / `.publisher` | NCKM 목록 메타 |
| `sourceUrl` | `source_documents.source_url` | view.do 링크 |
| `version` | `source_documents.release_date` 원문 | `"2024-07"` |
| `publishedAt` | `release_date` + 일자 보정 | `"2024-07"` → `"2024-07-01"` |

- 각 필드는 동명의 CLI 플래그(`--title` 등)로 덮어쓸 수 있다. 해당 `guide_idx` 행이 없으면
  종료코드 1 + stderr로 "먼저 `pnpm acquire:nckm`을 실행하라"고 안내한다.
- **청커는 이 조회에 관여하지 않는다** — 메타를 인자로 받는 순수 함수를 유지한다.
- **조회·보정 로직은 서비스에 둔다**(`domain/guideline`). CLI 스크립트는 인자 파싱과 파일 입출력만
  담당한다 — 수용 기준 12를 e2e로 동결하려면 검증 단위가 스크립트가 아니라 서비스 메서드여야 한다
  (§18의 `GuidelineAcquisitionService`와 같은 배치다).

### 대상 문서 구조 (비만 지침 실측 — `guide_idx=325`, 250p)

| 항목 | 값 |
|---|---|
| 인제스트 대상 | **Ⅳ. 권고사항** (인쇄 p.56~220, 물리 idx 64~228) — 그 외 장은 제외 |
| 권고 블록 마커 | **`【 R1 】`** 형식 (전각 대괄호). 문서 전체 **44개**, 전부 등급 파싱 가능 |
| 권고 번호 | `R1` ~ `R20`, 하위번호 `R1-1`·`R20-5` 포함 |
| 등급 표기 | `권고등급/근거수준` 결합: `A/High`×2 `B/Moderate`×14 `B/Low`×10 `C/Low`×14 `C/Very Low`×2, 합의 권고는 `GPP`×2 (합계 44) |
| 블록 내부 순서 | `【 R1 】` → 표 헤더(`권고안 권고등급/근거수준 참고문헌`) → 권고 문장 + 등급 + 참고문헌 번호 → `임상적 고려사항` → 소절(`(1) 배경` 또는 `(1) 임상질문`) → `① 개별 연구…` → `② 연구 결과의 요약` → `[참고문헌]` |
| 섹션 경로 | **페이지 헤더**에 있다: `["56", "IV 권고사항", "1 한의 단독 치료", "1) 한약"]` |
| 페이지 번호 | 물리 페이지 ≠ 인쇄 페이지. 각 페이지 **첫 줄이 인쇄 번호**다 (Ⅳ장 전 페이지에서 순수 숫자, 56~220 연속) |
| 제외 구간 | 영문 `Summary`(물리 21~30), 요약문, 목차, 진료알고리즘·확산도구(이미지), 부록 |

- **오프셋은 문서마다 다르므로 상수로 넣지 않는다** — 페이지 첫 줄의 숫자를 인쇄 번호로 그대로 읽는다.
  첫 줄이 순수 숫자가 아닌 페이지(장 표지 등)는 콘텐츠 페이지가 아니므로 건너뛴다.
- 등급 토큰은 **권고 문장 구간(표 헤더 다음 ~ `임상적 고려사항` 앞) 안에만** 존재한다
  (44블록 전수 확인, 구간 밖 0건). 구간을 한정해 파싱하면 해설 본문의 등급 언급에 오염되지 않는다 —
  실제로 해설에는 `권고등급 GPP를 부여하였다` 같은 서술이 2건 있어, 문서 전체를 스캔하면
  GPP가 4건으로 잡힌다. 블록의 권고 문장 구간만 보면 정확히 2건이다.

#### 페이지 헤더의 실제 형태 — 패리티가 아니라 레벨별 상속이다

각 페이지 헤더는 `인쇄번호` 다음에 **그 페이지가 새로 선언하는 레벨만** 싣고 나머지는 생략한다.
실측 분포(Ⅳ장 165페이지)는 다음과 같다.

| 헤더 2번째 줄 | 빈도 | 의미 |
|---|---|---|
| `IV 권고사항` | 83 | 장(chapter)만 — 인쇄면 기준 짝수 페이지 |
| `1 한의 단독 치료` | 30 | 1단계 절 — 인쇄면 기준 홀수 페이지 |
| `2 한의 복합 치료` | 52 | 〃 |

2단계 절(`1) 한약`, `5) 전침+일상 치료` 등 18개)은 **그 절이 시작하는 페이지에만** 나오고 이후
페이지에서는 생략된다. 즉 "짝수 페이지에 헤더가 없다"가 아니라 **어느 페이지든 선언된 레벨만
갱신하고 나머지 레벨은 직전 값을 상속**한다. 구현·fixture 모두 페이지 패리티에 의존하지 않는다.

- 1단계 절이 **바뀌면** 2단계 절을 초기화한다(같은 값이 반복 선언되는 러닝 헤더는 초기화하지 않는다).
- 장이 Ⅳ가 아닌 페이지는 청킹 대상에서 제외된다. 장은 로마 숫자 헤더(`IV 권고사항` → `V …`)에서
  갱신되며, 이 판정만으로 목차·요약문·영문 `Summary`·Ⅴ장 이후가 모두 배제된다.

#### 섹션 경로 정규화

페이지 헤더의 원문 표기를 다음 규칙으로 정규화해 `IngestSection.path`를 만든다.

| 원문 | 정규화 | 규칙 |
|---|---|---|
| `IV 권고사항` | `Ⅳ. 권고사항` | ASCII 로마 숫자 → 전각(U+2160~), 뒤에 `. ` |
| `1 한의 단독 치료` | `1. 한의 단독 치료` | 숫자 뒤에 `. ` |
| `1) 한약` | `1) 한약` | 그대로 |

`IngestSection.title`은 path의 마지막 요소, `order`는 등장 순서(0-based)다.
**청크가 하나도 없는 섹션은 출력하지 않는다.**

#### 하드 랩 복원 — 추출 텍스트의 줄바꿈은 문단 구분이 아니다

PDF 추출 결과의 `\n`은 **인쇄 지면의 시각적 줄바꿈**이다. 문장이 줄 중간에서 잘려
(`…한약 치료를 사용할 것을 권` / `고한다.`) 그대로 두면 `권\n고한다`가 되어 임베딩·인용·키워드
검색이 모두 깨진다. 따라서 청크 content를 만들 때 하드 랩을 복원한다.

| 판정 | 처리 |
|---|---|
| 줄이 **문장 종결부호**(`.` `?` `!` `。`, 뒤에 참고문헌 번호 `2)` `1,2)` `5-12)`가 붙을 수 있음)로 끝남 | 문단 끝 → `\n` 유지 |
| 그 외 | 하드 랩 → 다음 줄과 이어붙임 |

이어붙일 때: 앞줄이 하이픈으로 끝나고 뒷줄이 라틴 문자로 시작하면 **하이픈을 지우고** 붙이고
(`anti-obe-`+`sity` → `anti-obesity`), 양쪽이 라틴 문자·숫자면 **공백 하나**, 그 외(한글·한자 등)는
**줄 경계의 공백 글리프**로 정한다 — 있으면 공백 하나, 없으면 붙인다(아래 「어절 경계 줄바꿈」, #535 개정).

- 소제목·소절 마커 줄(`임상적 고려사항`, `(1) 배경`, `① 개별 연구 결과에 대한 설명` 등)은 항상
  문단 경계로 취급한다.
- 길이 기반 판정(짧은 줄 = 문단 끝)은 쓰지 않는다 — 실측에서 41자 줄이 문단 끝인 경우와 하드 랩인
  경우가 모두 나와 길이만으로는 구분되지 않는다.
- 문장이 지면 폭에 딱 맞아 끝나면 다음 줄이 같은 문단이어도 경계로 판정될 수 있다. `\n`이 하나 더
  생길 뿐 텍스트 손실이 없고 해설 분할 후보가 하나 늘 뿐이므로 허용한다.

##### 어절 경계 줄바꿈 — 줄 경계의 공백 글리프로 판정한다

> **개정 (issue #535, 2026-10-16).** 이 절의 원래 전제 — 「어절 경계의 공백은 양쪽 정렬이 흡수해
> **PDF가 인코딩하지 않으므로** 추출 방식을 바꿔도 복구되지 않는다」 — 는 틀렸다. 공백 글리프는 PDF에
> 있었고 **pdfjs가 버렸다.** 그래서 격조사로 공백을 추정하던 규칙(`을 를 이 가 은 는 의 에 로 와 과 도 만`으로
> 끝나면 공백)을 걷어 내고 공백 글리프로 판정한다. 옛 규칙의 측정 43/44는 요약문 권고 문장 44개라는 좁은
> 표본의 값이었고, 무작위 줄 경계 표본에서는 58/95였다.
>
> **교훈 — 「정보가 없다」는 결론은 그 정보를 본 도구의 결론이다.** 「추출 텍스트에 줄 끝 공백 0건, pdfjs 항목
> 단위로도 없다」는 실측은 pdfjs의 출력을 본 것이지 PDF를 본 것이 아니었다.

한글 줄바꿈은 **어중**(`…사용할 것을 권` / `고한다.`)과 **어절 경계**(`…기저질환이 있는` / `환자에게 …`)
양쪽에서 일어난다. 양쪽 정렬 지침 PDF(InDesign)는 어절 경계에서 줄을 바꾼 자리에 **줄 끝 공백 글리프를
실제로 갖고 있다** — 비만 지침(325) Ⅳ장의 한글–한글 줄 경계 2,796곳 중 876곳(31%)이고, 인제스트 대상
36문서 전부가 23~37%로 같은 분포다.

그 글리프가 사라진 것은 pdfjs 탓이다. `getTextContent`는 공백 글리프를 결과에 넣지 않고(evaluator의
`!keepWhiteSpace && isWhitespace → continue`) 글자 간격으로 공백을 다시 만드는데, 줄이 바뀌는 자리에는
잴 간격이 없으니 공백도 없다. `keepWhiteSpace` 옵션은 공개 API(`page.getTextContent()`)에 없고 내부에서는
주석 외형 추출에만 켜진다 — 그래서 unpdf 번들에 패치를 건다(아래 「패치 방식과 업그레이드 주의」).

**판정 규칙** — 하드 랩을 이을 때 위에서부터 처음 맞는 줄을 쓴다(`appendWrapped`):

| # | 조건 | 처리 | 예 |
|---|---|---|---|
| 1 | 앞줄이 하이픈으로 끝남 | 공백 없이. 뒷줄이 라틴 문자면 하이픈을 지운다(개정 전 그대로) | `anti-obe-`+`sity` → `anti-obesity` |
| 2 | 뒷줄이 `-`+라틴 문자로 시작하고 앞줄이 라틴 문자·숫자로 끝남 | 공백 없이 | `meta`+`-analysis` → `meta-analysis` |
| 3 | 양쪽이 라틴 문자·숫자 | 공백 하나(개정 전 그대로) | `Visual Analogue`+`Scale` |
| 4 | 그 밖(한글·한자·괄호 등이 낀 경계) | **경계에 공백 글리프가 있으면 공백 하나, 없으면 붙인다** | 아래 표 |

경계의 공백 글리프는 ① 앞줄 끝 ② 뒷줄 첫머리 ③ 두 줄 사이의 공백만 있는 줄 — 셋 중 어디에 있어도 된다.

| 앞줄 끝 | 뒷줄 | 결과 | 개정 전(격조사 추정) |
|---|---|---|---|
| `…기저질환이 있는␠` | `환자에게 …` | `있는 환자에게` | 같음 |
| `…식이 조절을 통해␠` | `대사량을 …` | `통해 대사량을` | `통해대사량을` |
| `…복용 중 이` | `상반응이 …` | `이상반응이` | `이 상반응이` |
| `…두 차례 평가` | `되었다.` | `평가되었다.` | `평가 되었다.` |
| `…감소하였으나1-3)` | `␠이완기 혈압은 …` | `1-3) 이완기` | (개정 전 추출에서는 한 줄) |

- **근거**: 무작위 줄 경계 100건(판정 95)에서 격조사 추정 58/95, 글리프 판정 94/95다. 판본 3종(325·163·314)에서
  격조사 추정이 글리프와 일치한 비율은 66%·74%·57%뿐이었다.
- **라틴 문자·숫자 경계는 글리프와 무관하게 공백을 넣는다(규칙 3).** 글리프가 없는 라틴·숫자 경계는 대부분
  표 칸·목차·쪽 머리처럼 서로 다른 요소 사이였다(`critical`⏎`471`, `CHAPTER`⏎`03`).
- **하이픈 경계도 글리프와 무관하다(규칙 1·2).** 하이픈 뒤에 글리프가 있는 줄바꿈(대상 문서 청크 본문 21곳)은
  낱말 안 줄바꿈(`interven-`⏎`tion`)과 복합어(`IVA-`⏎`CPT`)가 반반이라 글리프가 둘을 가르지 못하고,
  글리프를 따르면 둘 다 `X- Y`가 된다. 하이픈 앞 글리프(`methyl␠`⏎`-phenidate`, 52곳)를 따르면
  `methyl -phenidate`가 된다.
- **뒷줄 첫머리 글리프**: 위첨자 참고문헌 번호 뒤에서 pdfjs가 공백에서 줄을 새로 연다
  (`…으로1-3)`⏎`␠높았고` — 163). 앞줄 끝만 보면 그 경계가 붙는다(대상 문서 청크 본문 292곳).
- **줄 안 공백 정규화**: 공백 글리프를 살리면 줄 안에 공백이 두 칸 이상 붙기도 한다(325에서 1,121곳).
  페이지를 줄로 나누는 모든 곳(`splitPageLines`)이 연속 공백·탭을 한 칸으로 합친 뒤 trim한다 — 그러면 325
  Ⅳ장 165쪽 전부가 개정 전 추출과 같아지고, 163·314에서 남는 차이는 글머리 기호 뒤 공백 복원
  (`•뜸치료` → `• 뜸치료`)뿐이다. 합치지 않으면 헤더의 이중 공백 때문에 섹션 경로가 갈라진다.
- **공백만 있는 줄**: 공백 글리프가 혼자 한 줄로 떨어지기도 한다(163에서 78줄). trim 뒤 빈 줄이라 건너뛰되,
  그 줄 자체가 위아래 줄 사이의 공백 글리프이므로 경계 판정에는 넘긴다.
- **형태소 분석기는 여전히 넣지 않는다** — 순수 함수 설계(모델 로딩·async·사전 의존 없음)를 지키고, 남은
  오류(아래 표 칸)는 레이아웃 문제라 형태소로 풀리지 않는다.
- 검증: `guideline-chunker.spec`의 「spec 19 개정(#535)」 a~f(합성 fixture), `pdf-text.extractor.spec`(패치 회귀).

**패치 방식과 업그레이드 주의**

- `patches/unpdf@1.8.0.patch`가 unpdf 번들 pdfjs(`dist/pdfjs.mjs`)의 워커 페이지 텍스트 추출 호출
  (`extractTextContent`의 `getTextContent({…, intersector:a}`) **한 곳**에만 `keepWhiteSpace:!0`을 더한다.
  선언은 `package.json`의 `pnpm.patchedDependencies`, 해시는 `pnpm-lock.yaml`에 있고, `Dockerfile`은 설치
  전에 `patches/`를 복사한다(없으면 frozen 설치가 패치 파일 ENOENT로 실패한다).
- 번들이 압축돼 있어 패치가 긴 한 줄을 통째로 담는다 — **unpdf를 올리면 패치가 맞지 않으니** 새 번들에서
  같은 호출을 찾아 다시 만든다. 패치가 빠진 채 지나가지 않게 `pdf-text.extractor.spec`이 줄 끝 공백
  보존(`'hello \nworld'`)을 본다. jest vm은 unpdf의 ESM 번들 동적 import를 막으므로 이 테스트는 추출만
  자식 node 프로세스에서 돌린다.
- 설치된 번들을 손으로 고쳤다면 `pnpm install --frozen-lockfile`로는 되돌아오지 않는다(「Already up to
  date」 — 설치된 파일 내용을 다시 검사하지 않는다). `--force`로 다시 설치한다.
- 추출기는 페이지를 하나씩 추출하고 놓는다(unpdf `extractText`의 전 페이지 `Promise.all` 대신). 출력은
  같고(51문서 문자열 동일) 로컬 최대 RSS(MiB, #174/#232/#153)가 564/518/380에서 434/451/172로 줄었다.
  `keepWhiteSpace` 자체의 메모리 비용은 0이다.

**알려진 한계**

- **한글 표 칸 경계에는 공백 글리프가 없어 칸끼리 붙는다**(`결과중요도`⏎`총 환자 수` → `결과중요도총 환자 수`).
  무작위 표본 100건 중 4건이었다. 개정 전에는 격조사로 끝나는 칸에만 공백을 넣었다(`결과`⏎`결과중요도` →
  `결과 결과중요도`) — 이제는 그 칸도 붙는다.
- 위첨자 번호 뒤에서 pdfjs가 줄을 새로 열면 앞줄이 문장 종결(`…있다.4)`)로 끝나 문단 경계가 하나 더 생긴다
  (163). 글자 손실은 없다 — 위 「하드 랩 복원」에서 문장이 지면 폭에 딱 맞아 끝나는 경우와 같은 허용이다.

**재적재 영향(개정 전 출력 대비, 인제스트 대상 36문서)**: 권고 번호·등급·근거수준·섹션 경로가 전부 같고,
공백을 지운 본문도 전부 같다. 청크 3,863 → 3,873 — 본문이 같은 청크 573(14.8%), 공백만 다른 청크
3,033(78.5%), 해설 2,000자 분할 경계가 옮겨 간 청크 257(6.7%)이다. 공백이 늘어 누적 길이가 먼저 2,000자를
넘기 때문이다(비만 325는 152 → 154).

## 청킹 전략

권고문 하나당 **2종 청크**를 만들고, 같은 `recommendationNumber`로 묶는다.

| 청크 | content | 메타데이터 |
|---|---|---|
| **권고문**(1차) | 권고 문장 + `임상적 고려사항` | `recommendationNumber`, `recommendationGrade`, `evidenceLevel`, `pageStart/End` |
| **근거 해설**(2차) | 소절 시작(`(1) 배경` 또는 `(1) 임상질문`)부터 `[참고문헌]` 앞까지 | 같은 `recommendationNumber`, 등급은 **비운다** |

- 권고문 청크가 검색의 핵심 단위다. `임상적 고려사항`을 붙이는 이유는 "무엇을 권고하는가"와
  "어떤 환자에게 어떻게"가 붙어 있어야 임상적으로 쓸 수 있는 답이 되기 때문이다.
- 권고문 청크 content에서 **`【 R1 】` 마커 줄과 표 헤더 줄(`권고안 권고등급/근거수준 참고문헌`)은
  제외**하고, 권고 문장 끝의 **등급 토큰과 그 뒤 참고문헌 번호도 제거**한다
  (`…권고한다. A/High 5-12)` → `…권고한다.`). 등급은 메타데이터로 이미 기록되고, 참고문헌 번호는
  가리킬 서지 목록을 버리므로 본문에 남기면 의미 없는 잔여물이 된다. 실측 44블록 모두 등급 토큰
  뒤에는 참고문헌 번호(또는 `-`)만 온다.
- **청크가 속하는 섹션은 그 블록이 시작하는 페이지의 경로**로 정한다. 블록이 페이지를 넘어가도
  섹션은 바뀌지 않는다(실측에서 새 절은 항상 새 블록으로 시작한다).
- 각 청크의 `pageStart`/`pageEnd`는 그 청크의 **첫 줄과 마지막 줄이 놓인 인쇄 페이지**다.
  한 페이지에서 앞 블록의 해설이 끝나고 다음 블록이 시작하면 두 청크의 페이지 범위가 겹칠 수 있다 —
  정상이다.
- 해설 청크에 등급을 **복사하지 않는다.** 등급은 권고에 부여된 것이지 해설 문단에 부여된 것이 아니다 —
  복사하면 "근거수준 High" 인용이 해설 문단을 가리키게 되어 근거가 실제보다 강해 보인다.
- **해설 시작 경계는 `(1) 배경`이 아니라 "`임상적 고려사항` 본문 다음의 첫 소절 마커"다.**
  하위번호 블록 8개(R1-1·R1-2·R1-3·R8-1~R8-5)에는 `(1) 배경`이 없고 `(1) 임상질문`으로 시작한다.
  소절 마커는 `(숫자)` 또는 `①②③…`이며, 줄 첫머리에서만 인식한다
  (`(六君子湯)…`처럼 한자 줄바꿈으로 생기는 괄호 시작 줄과 구분하기 위해 **괄호 안이 숫자일 때만** 마커다).
- **`[참고문헌]` 줄부터 블록 끝까지는 버린다.** 서지 목록은 위 표가 정의한 해설 content(배경·개별
  연구·요약 본문)가 아니며, 문헌 나열로만 이루어진 청크가 생기면 검색·인용 품질이 떨어진다.
- 해설이 길면 문단 경계로 분할하되 `recommendationNumber`는 유지한다. 분할 기준은 **누적 2,000자를
  넘기 직전의 문단 경계**이며, 분할된 청크도 각각 자기 구간의 `pageStart`/`pageEnd`를 갖는다.
- 섹션(`IngestSection`)은 페이지 헤더에서 만든 경로 단위로 묶고, `path`는
  `["Ⅳ. 권고사항", "1. 한의 단독 치료", "1) 한약"]` 형태로 정규화한다.

### 블록 경계

블록을 **표지 줄을 만나는 순서대로** 구간(권고 문장 / 고려사항 / 해설 / 참고문헌)으로 끊는다.
구간마다 기대하는 경계를 하나씩 정해두고 **못 찾으면 블록 끝으로 떨어지는 폴백을 쓰지 않는다.**

그 폴백이 실제로 무너진 자리다(issue #98). 판본이 그 경계를 안 쓰면 구간이 블록 전체를 삼켜,
권고문 청크에 해설 전문과 참고문헌 서지가 통째로 들어갔다 — 실물 31건에서 권고문+해설 671쌍 중
**100쌍**이 이 상태였고 같은 텍스트가 두 번 적재됐다. 그중 13건은 임베딩 8,192토큰 상한을 넘겨
문서째 적재에 실패했다(최대 22,577토큰).

**어느 경계가 먼저 오는지 가정하지 않는다.** 실물에서 관측된 배치가 판본마다 다르기 때문이다:

| 배치 | 실물 |
|---|---|
| 정순 — 권고문 → 고려사항 → 해설 → 참고문헌 | 325(비만) 외 다수 |
| 고려사항 제목이 아예 없음 | 163·170·351·141 |
| 고려사항이 해설보다 **뒤**에 옴 | 149 |
| 고려사항이 해설 **중간**에 끼어 해설이 두 동강 남 | 149 R2·R4 |
| `[참고문헌]` 표지가 없음 | 163·170·149 |

- 고려사항 제목은 `임상적 고려사항`과 대괄호 표기 `[임상적 고려사항]`을 모두 받는다. 두 표기가
  잇달아 나오는 판본이 있으므로 **먼저 오는 쪽**이 경계다.
- 해설이 고려사항으로 갈라지면 **앞뒤 조각을 모두** 해설 청크로 살린다. 권고문 청크는 떨어져 있는
  고려사항 구간을 권고 문장 뒤에 이어 붙인다 — §「청킹 전략」 표의 정의가 지면 순서가 아니라
  구간 종류로 내려지기 때문이다.
- `[참고문헌]` 표지가 **없는** 판본에서는 서지 시작을 알 수 없어 해설 청크에 서지가 남는다
  (실물 13문서 220청크). 표지 없는 서지 탐지는 별도 과제이며, 수용 기준 10은 표지가 있는 판본에
  대한 규범이다.

### 청크 길이 상한

**모든** 청크는 6,000자를 넘지 않는다. 넘으면 §「청킹 전략」의 해설 분할과 같은 방식으로 문단
경계에서 끊고, 문단 하나가 그보다 길면 문장 경계에서, 그마저 없으면 상한 위치에서 강제로 끊는다.

- 이는 **안전망**이지 청킹 전략이 아니다. 경계가 제대로 잡힌 청크는 이 길이에 한참 못 미친다
  (실물 최장 2,990토큰). 미지 판본에서 경계 검출이 다시 무너져도 임베딩 API가 400을 뱉는 대신
  분할로 처리돼 그 문서가 통째로 유실되지 않게 하는 것이 목적이다.
- 값의 근거: OpenAI 임베딩 입력 상한은 8,192토큰이고, 실물 31건 2,881청크에서 cl100k_base
  토큰/문자 비율은 p50 0.921 · p99 1.234 · **max 1.313**이다. 6,000자면 최악 7,878토큰이다.
- **토크나이저를 파싱 단계에 넣지 않는다** — 문자 수로 근사하고 그 대가로 여유를 크게 잡는다.
  형태소 분석기를 넣지 않는 것과 같은 이유로, 순수 함수 설계(모델 로딩·async·사전 의존 없음)를 지킨다.
- 권고문 청크가 분할되면 **등급은 첫 조각에만** 남긴다. 뒤쪽 조각에까지 복사하면 같은 번호로 등급
  있는 청크가 둘이 되어 §20의 `duplicated` 진단이 재인용 오인으로 오작동한다.

### 등급 매핑

`IngestRating`은 `{system, code, label}` 3필드가 모두 필수다. `code`는 **원문 표기를 보존**하고,
`label`은 지침 §III(p.52)이 정의한 한국어 표현을 쓴다. `system`은 양쪽 모두 `'GRADE'`다
(GPP도 이 지침의 GRADE 운용 안에서 부여되는 등급이다).

| 원문 | recommendationGrade | evidenceLevel |
|---|---|---|
| `A/High` | `{GRADE, 'A', '강한 권고'}` | `{GRADE, 'High', '높음'}` |
| `B/Moderate` | `{GRADE, 'B', '중등도 권고'}` | `{GRADE, 'Moderate', '중등도'}` |
| `B/Low` | `{GRADE, 'B', '중등도 권고'}` | `{GRADE, 'Low', '낮음'}` |
| `C/Low` | `{GRADE, 'C', '약한 권고'}` | `{GRADE, 'Low', '낮음'}` |
| `C/Very Low` | `{GRADE, 'C', '약한 권고'}` | `{GRADE, 'Very Low', '매우 낮음'}` |
| `D/*` | `{GRADE, 'D', '권고하지 않음'}` | 근거수준 표기대로 |
| `GPP` | `{GRADE, 'GPP', '전문가 합의 권고'}` | **없음** |

`D`는 이 문서에 나오지 않는다(방어적 매핑). 근거수준 파싱은 `Very Low`를 `Low`보다 먼저 시도해야
공백이 든 표기가 잘리지 않는다.

## 수용 기준 (= 동결할 시나리오, Definition of Done)

**청커(순수 함수) — 합성 텍스트 fixture 기반 단위 테스트**

> fixture는 위 「대상 문서 구조」 표의 실측 형식을 그대로 모방하되 내용은 창작한다.
> 최소 구성: Ⅳ장 페이지 — 장만 선언한 러닝 헤더 페이지 / 1단계 절만 선언한 페이지 / 2단계 절까지
> 선언한 절 시작 페이지, 등급이 다른 권고 블록 3종 이상(`A/High`·`C/Very Low`·`GPP`),
> 하위번호 블록(`R1-1`, `(1) 배경` 없이 `(1) 임상질문`으로 시작), `[참고문헌]`이 붙은 블록,
> 영문 `Summary` 1페이지, Ⅳ장 밖 페이지(목차 등) 1페이지, Ⅴ장 페이지 1개.

1. 페이지 텍스트를 넣으면 **`【 R 】` 블록 수만큼 권고문 청크**가 나오고,
   각 청크의 `recommendationNumber`가 블록 마커와 일치한다
2. `A/High` → `recommendationGrade {system:'GRADE', code:'A', label:'강한 권고'}` +
   `evidenceLevel {system:'GRADE', code:'High', label:'높음'}`로 **분리 매핑**된다.
   `C/Very Low`처럼 공백이 든 근거수준도 정확히 파싱된다 (매핑표는 「등급 매핑」 참조)
3. `GPP`는 `recommendationGrade.code='GPP'`로 기록되고 `evidenceLevel`은 **비어 있다**
   (등급 체계상 근거수준이 없는 합의 권고이므로 없는 값을 만들어내지 않는다)
4. 권고문 청크의 `content`에 권고 문장과 `임상적 고려사항`이 **모두** 포함되고,
   `【 R 】` 마커·표 헤더·등급 토큰·참고문헌 번호는 **포함되지 않는다**
5. 지면에서 줄 중간에 잘린 문장이 **하드 랩 복원되어** 한 문장으로 이어진다
   (`…권` + `고한다.` → `…권고한다.`). 문장 종결로 끝난 줄은 문단 경계로 남는다
6. 해설 청크는 같은 `recommendationNumber`를 갖고 `recommendationGrade`·`evidenceLevel`이 **비어 있다**.
   `(1) 배경`이 없는 하위번호 블록도 `(1) 임상질문`부터 해설 청크가 만들어진다
7. `sectionPath`가 페이지 헤더에서 정규화되어 나오고, **선언되지 않은 레벨은 직전 값을 상속**한다
   (2단계 절은 절 시작 페이지에만 선언된다). 1단계 절이 바뀌면 2단계 절은 초기화된다
8. `pageStart`/`pageEnd`가 **인쇄 페이지 번호**로 기록된다 (물리 인덱스가 아니다 — 각 페이지 첫 줄에서 읽는다)
9. 영문 `Summary` 구간과 Ⅳ장 밖(목차·요약문·Ⅴ장 이후)의 텍스트는 **어떤 청크에도 포함되지 않는다**
10. **`[참고문헌]` 이후의 서지 목록이 어떤 청크에도 포함되지 않는다**
11. 출력이 `GuidelineIngestInput`의 필수 필드를 모두 채워 **기존 `GuidelineIngestService.validate`를 통과**한다

**파이프라인 연결 — e2e**

12. 파싱 결과 JSON을 `GuidelineIngestService.ingest`에 넣으면 **블록 수만큼의 권고문 청크**
    (+ 해설 청크)가 적재되고, `recommendationNumber`로 조회한 권고문 청크의 등급이 원문 표기와
    일치하며 같은 번호의 해설 청크는 등급이 비어 있다
13. `--guide-idx`로 지정한 문서의 메타(`title`·`publisher`·`sourceUrl`·`version`·`publishedAt`)가
    `source_documents`에서 채워지고, 해당 행이 없으면 실패한다

  입력으로 쓰고, 추출 경로는 CLI 수동 실행으로 확인한다. 단 **`keepWhiteSpace` 패치 회귀 테스트 1건**
