# 53. 환자 맞춤 검색 입력 — 환자 대화의 검색도 진단명을 딛고, 턴이 그 기록을 가리킨다

## 목표

환자 고정 대화(PATIENT_GUIDANCE)에서 **병명을 생략한 질문도 그 환자의 질환 지침에서 근거를 찾는다.** 끝나면 「이 환자에게
침 치료를 고려할 때 주의할 점은?」의 검색·리랭크 입력에 복합 경로(§51)와 같은 규칙으로 그 환자의 진단명이 붙고, 답변 턴은
**검색 전에 고정한 스냅샷**을 가리킨다.

§51이 「환자 고정 대화는 질문이 병명을 쓴다(37/37)」로 남겨 둔 전제를 고친다 — 그 37건은 병명이 든 추천 질의문이었다.
에이전트·FE는 바뀌지 않는다.

## 실측 조사 (2026-09-20, BE·FE 코드 + 운영 DB + 로컬 `hybrid_probe` 프로브)

### 「질문이 병명을 쓴다」는 추천 질의문의 성질이다 (운영 `messages`, 08-11~09-20)

| 확인 | 실측 |
|---|---|
| PATIENT_GUIDANCE 질문 | 38건(고유 12) — **32건(84%)이 추천 질의문 6종**(3문장 × ko·en, `suggested-prompts.ts:69-91`)을 그대로 누른 것이고 세 문장 모두 병명을 담는다 |
| 병명을 생략한 질문 | **1건** — 「이 환자에게 침 치료를 고려할 때 주의할 점은?」(09-14, 골다공증 환자) → `ABSTAINED` `insufficient_evidence` |
| 진단명과 질문의 표기가 다르다 | 9건(24%) — CASE-002의 진단은 「주의력결핍 과잉행동장애」, 질문은 전부 「ADHD」 |
| 질문의 병명이 환자 진단이 아닐 수 있다 | 4건 — 진단이 추천 키워드에 안 걸리는 환자(CASE-004·005)에게는 편두통·불면·전립선 일반 예시가 뜬다(`suggested-prompts.ts:126`). 그 환자들의 진단은 암호화 필드라 조회하지 않았다 |
| 오늘의 검색 입력 | 환자 대화는 질문 원문만 쓴다(`conversation-stream.service.ts:381` `diagnoses: []`). 환자 기록은 검색 게이트를 통과한 **뒤에** 읽어 생성 프롬프트에만 합성한다(`:439-455`) |
| 복합 경로 | 환자 도구가 검색 **전에** 스냅샷을 만들어 `agent_turns.patient_snapshot_id`에 고정하고, 근거 도구가 그 진단명을 번역 뒤 검색 입력과 리랭크 질문에 붙인다(`:597-602`). 운영 2건 모두 병명을 생략했다(「…에게 침 치료해도 돼? 골다공증」) |

### 부착 유무 프로브 — 운영과 같은 경로(하이브리드 → 거리 게이트 → 리랭크 → 점수 컷 9 → top-5), 1회 실행

참고안 평가의 정렬 케이스 24문항(`guidance-eval.cases.ts` — 문항 주제와 진단이 만나는 합성 프로필)에서 병명만 지운 변형
(「○○ 환자에게」→「이 환자에게」)을 만들고, 진단명을 공백으로 이어 붙인 입력과 대조했다. 코퍼스는 운영과 같은 ACTIVE
7,154청크다. 「지침 점유」는 top-5 중 그 질환 지침에서 온 근거 수다.

| 입력 | 기권(거리·점수) | 정답 근거 top-5 | 지침 점유 |
|---|---|---|---|
| 병명 있음 · 안 붙임 (오늘) | 0 | 24/24 | 4.83/5 |
| 병명 있음 · 진단명 부착 | 0 | 24/24 | 4.88/5 |
| 병명 있음 · **다른** 진단명 부착(고혈압) | 0 | 24/24 (정답 평균 순위 1.08 → 1.25) | 4.92/5 |
| **병명 생략 · 안 붙임 (오늘)** | **3** (1·2) | **18/24** | **2.67/5** |
| **병명 생략 · 진단명 부착** | **0** | **23/24** | **4.88/5** |
| 병명 생략 · 진단 2개 부착 | 0 | 23/24 | 4.75/5 |

- **오늘의 실패는 기권보다 「다른 질환 근거로 통과」다.** 병명을 생략하고도 게이트를 넘은 21문항 중 10문항은 top-5의 과반이
  다른 질환 지침이었다 — 류마티스 환자의 「이 환자의 증상 개선을 위해 한약치료를…」은 임신오조 4건 + 과민대장증후군 1건으로
  점수 9를 받아 통과했다.
- 부착 뒤 놓친 1건(전립선)은 5건 모두 같은 지침의 다른 권고였다.
- **언급 판정은 값을 하지 못한다.** 「질문이 진단명을 담고 있으면 붙이지 않는다」(공백 제거·소문자 부분문자열)를 모사하면
  24문항 중 7문항이 판정을 빗나가 어차피 붙고(「ADHD」·「원발성 불면」·「유방암 치료 후」…), 결과는 항상 붙이는 쪽과 같다
  (24/24 · 4.88).
- 막연한 질문 3종(운영의 그 질문 포함) × 진단 6종: 진단명 없이는 2종이 기권하고 **1종은 임신오조·편두통·우울증 근거로
  통과**했다. 붙이면 18건 중 13건이 통과하고 통과한 근거는 그 질환 지침이다(점유 5/5). 「요통」은 3종 모두 점수 8로 기권했다.

### 기존 구조와의 접점

| 확인 | 실측 |
|---|---|
| 평문 기록 | `generation_runs.search_question`은 평문이고 복합 경로는 이미 붙인 문자열을 남긴다(§51 기준 51·104). 환자 대화의 답변 31/36·참고안 요약 31/36이 이미 같은 병명을 평문으로 담는다 |
| 파기 순서 | 메시지·스냅샷을 지우는 곳은 `data-purge.repository.ts` 하나다. 대화 파기가 메시지를, 환자 파기가 스냅샷을 지우며 클리닉 파기도 대화 → 환자 순이다(`:167-173`) |
| 환자 파기 보류 | 그 환자를 가리키는 대화가 남아 있으면 환자를 뽑지 않는다(#473, `:55-75`). 환자 대화의 스냅샷은 언제나 `conversations.patient_id`의 것이다 |
| 공개 계약 | `MessageResponseDto`에 스냅샷 필드가 없다 — 참고안 id만 나간다 |
| 동결된 이웃 기준 | §51 기준 104·105(근거 도구)는 질문에 진단명이 없는 경우라 그대로 성립한다. §40 기준 28(생성 게이트 기권에도 스냅샷 1건)도 그대로다. 검색 게이트 기권 턴의 스냅샷 유무를 동결한 기준은 없다 — §10은 「스트림 시작 시 캡처」를 말했고 구현이 그것을 생성 직전으로 미뤄 두었을 뿐이다. 스냅샷만 남고 참고안이 없는 상태는 이미 있다(§40 실측) |

## 판단 근거 (2026-09-20 사용자 확정)

| 쟁점 | 판단 |
|---|---|
| 부착 규칙 | **항상 붙인다 — 환자 대화도 복합 경로와 같은 규칙이다.** 번역(§42) 뒤의 검색 입력과, 사용자가 쓴 질문을 보는 리랭크 질문(§29) 양쪽에 그 턴 스냅샷의 진단명을 기록된 순서대로 공백으로 잇는다. 근거 도구는 바뀌지 않는다. **기각**: 질문이 진단명을 언급하지 않을 때만 — 측정 결과가 같고(24/24 · 4.88), 표기가 갈리는 운영 질문 24%에서 판정이 어차피 빗나가며, 정규화·부분문자열·짧은 진단명 예외가 두 경로에 새로 생긴다 |
| 붙이는 필드 | **진단명만.** 투약·알레르기·임상 메모는 생성 프롬프트에만 간다(오늘 그대로). 임상 메모는 자유 텍스트 4,000자라 검색어로 쓰면 질문을 덮는다 |
| 기록을 읽는 시점 | **검색 전에 스냅샷을 만들어 그 답변 메시지에 고정한다(`messages.patient_snapshot_id`) — 복합 경로와 같은 순서·같은 참조 방식이다.** 검색의 진단명, 생성 프롬프트의 프로필, 참고안이 모두 그 스냅샷 하나를 딛는다. 검색 결과가 환자 기록에 좌우되기 시작하므로 기권한 턴도 「어느 기록을 봤나」가 남아야 붙인 진단명을 되짚을 수 있다(§5.7 재현성, `agent_turns`와 같은 이유). §40 기준 28이 남기던 참조 없는 스냅샷도 이제 턴이 가리킨다. **기각**: 한 번 읽고 게이트 통과 뒤에 스냅샷(스키마 무변경이나 기권 턴에 흔적이 없고 두 경로의 구조가 갈린다) · 스냅샷만 검색 앞으로(기권 턴에 참조 없는 암호화 사본이 남는다) · 진단명만 따로 읽기(두 번 읽는 사이 기록이 바뀌면 검색과 생성이 다른 기록을 본다) |
| 검색 기록 | **붙인 그대로 `search_question`에 남긴다 — 복합 경로와 같은 규칙이다**(§51 기준 51·104). 기록만으로 실제 검색 입력이 재현된다. 암호화 필드의 값이 평문 컬럼에 실리지만 새 종류의 노출이 아니다(실측) — 그 행들의 수명은 환자 삭제 연쇄(§34)가 환자에 묶는다. **기각**: 붙이기 전 문자열만(복합 경로와 규칙이 갈리거나 §51 기준 104를 재동결해야 하고, 재현에 스냅샷 복호화가 든다) |
| 기존 턴 | **백필하지 않는다.** 이 컬럼은 「검색 전에 고정한 기록」인데 옛 턴의 검색은 환자 기록을 쓰지 않았다 — 참고안의 스냅샷 id로 채우면 사실이 아닌 값을 말한다. NULL은 「이 스텝 이전의 턴」이다(§43이 NULL을 「기록되기 전의 행」으로 읽는 것과 같다) |

**위험.**
- ⑴ **검색 게이트가 막연한 질문을 더 통과시킨다.** 「침 치료해도 돼?」가 ③을 넘어 LLM 비용과 게이트 ④에 닿는다 — 의도한 방향이고, 통과한 근거는 그 질환 지침이다(실측).
- ⑵ **질문의 병명이 환자 진단과 다르면 진단명이 그 검색에 섞인다**(운영 4/38). 측정은 24/24였지만 방해 진단을 한 종류(고혈압)만 쟀다.
- ⑶ **다중 진단은 전부 붙는다**(23/24 · 4.75). 데모 환자 3종은 모두 단일 진단이라 운영 표본이 없다.
- ⑷ **진단명은 자유 텍스트다** — 「산후풍 의심」·「우측 슬관절 전치환술 후」 같은 수식어가 그대로 검색어가 된다(측정에 포함).
- ⑸ **측정의 한계.** 병명 생략 문항은 역생성 평가 문항의 변형이라 정답 청크와 어휘가 겹친다(낙관 편향) — 그래서 막연한 질문군을 따로 쟀다. LLM 리랭커 점수는 실행마다 흔들리는데 이번은 1회 실행이다 — 운영에서 ③을 넘었던 그 질문(09-14)이 프로브에서는 점수 3으로 기권했다.
- ⑹ **기권한 턴에도 암호화 사본이 1건씩 생긴다**(운영 검색 게이트 기권 1/38).

## 수용 기준 (= 동결할 e2e 시나리오, Definition of Done)

**환자 대화의 검색이 진단명을 딛는다**

1. 환자 대화 턴의 `generation_runs.search_question`이 질문 뒤에 그 환자의 진단명을 공백으로 이은 문자열이다 (e2e)
2. 검색에 들어간 질의(임베딩 입력)가 그 `search_question`과 같다 (e2e — 기록하는 가짜 임베딩. 기록만 바뀌고 검색은 그대로인 구현을 막는다)
3. 진단이 둘 이상이면 기록된 순서대로 모두 붙는다 (e2e)
4. 질문이 이미 그 진단명을 담고 있어도 붙는다 (e2e — 언급 판정을 두지 않는다, 실측)
5. 진단이 없는 환자면 `search_question`이 질문 그대로다 (e2e)
6. 리랭커가 받는 질문은 사용자가 쓴 질문 뒤에 같은 진단명이 붙은 문자열이다 (e2e — 기록하는 가짜 리랭커, §51과 같은 규칙)
7. 영문 질문이면 번역기 입력에 진단명이 없다 (e2e — §51 기준 105와 같은 이유)
8. 그때 `search_question`은 번역문 뒤에 진단명이 붙은 문자열이다 (e2e)
9. 생성 LLM이 받는 질문은 오늘의 프로필 합성 질문 그대로다 — 뒤에 진단명이 덧붙지 않는다 (e2e — 부착은 검색·리랭크 입력에만)
10. `generation_runs.original_question`은 사용자가 쓴 질문 그대로다 (e2e — 회귀)

**턴이 검색 전에 고정한 스냅샷을 가리킨다**

11. 환자 대화 턴이 완료되면 ASSISTANT 메시지의 `patient_snapshot_id`가 그 환자의 스냅샷을 가리킨다 (e2e)
12. 그 턴에서 스냅샷은 1건만 늘어난다 (e2e — 검색용과 생성용을 따로 만들지 않는다)
13. 그 턴 참고안의 `patient_snapshot_id`가 메시지의 것과 같다 (e2e — 검색·생성·참고안이 같은 기록을 딛는다)
14. 검색 게이트에서 기권한 턴에도 메시지가 스냅샷을 가리킨다 (e2e — 붙인 진단명을 되짚을 수 있다)
15. 그때 generation run이 없다 (e2e — §8 「run 없음 = 검색 게이트」 회귀)
16. 그때 참고안이 없다 (e2e — 회귀)
17. 생성 게이트에서 기권한 턴에도 메시지가 스냅샷을 가리킨다 (e2e — §40 기준 28의 스냅샷이 이제 참조된다)
18. 환자 대화의 USER 메시지는 `patient_snapshot_id`가 NULL이다 (e2e)
19. 일반 대화의 ASSISTANT 메시지는 `patient_snapshot_id`가 NULL이다 (e2e)

**다른 경로와 공개 계약은 그대로다**

20. 일반 대화의 `search_question`은 질문 그대로다 (e2e — 회귀)
21. 메시지 목록 응답에 스냅샷 id가 없다 (e2e)
22. 커밋된 OpenAPI가 바뀌지 않는다 (contract)

**새 FK가 파기를 막지 않는다**

23. 환자를 삭제하고 유예가 지나면 파기가 그 환자 대화와 스냅샷·환자를 오류 없이 지운다 (e2e — 메시지 → 스냅샷 순, §51 기준 120과 같은 이유)
24. 클리닉 파기가 환자 대화가 있는 클리닉을 오류 없이 지운다 (e2e — 대화 → 환자 순)

fixture 규약:
- **환자 기록·질문·근거는 구조를 모방한 합성 텍스트다** — 데모 환자 원문과 운영 질문을 쓰지 않는다. 진단명은 `합성진단-<ulid>`처럼 코퍼스에 없는 값이다(§51 기준 104와 같은 방식).
- **e2e는 §13대로 Testcontainers에 fake LLM·임베딩·리랭커·번역기를 쓰고, 각 가짜는 받은 입력을 기록한다**(기준 2·6·7·9). 거리 컷은 기존 스위트처럼 넓혀 가짜 임베딩이 게이트 ①을 넘게 한다.
- **근거 도구의 회귀 가드는 §51 기준 104·105 스위트**(`agent-turn-patient-evidence.e2e-spec.ts`)이고, 환자 대화의 회귀 가드는 기존 스위트(§10·§33·§40·§42·§44)다 — 이 스텝은 그 스위트들의 단언을 바꾸지 않는다.
- **이 문서의 수치는 단언 대상이 아니다** — 프로브 결과(24문항·막연한 질문군)와 운영 분포는 환경의 성질이다. 동결하는 것은 부착 규칙·부착 위치(검색·리랭크에만)·스냅샷 고정 시점·참조 일치·파기 순서다.

## Out of scope

- **언급 판정·진단명 정규화·동의어 사전**(「ADHD」↔「주의력결핍 과잉행동장애」) — 측정상 부착만으로 회수된다.
- **진단명 밖의 필드를 검색에 쓰는 것** · **질문의 병명이 환자 진단과 다를 때의 처리**(위험 ⑵) — 운영 표본이 쌓인 뒤 판단한다.
- **추천 질의문 개편** — 진단이 키워드에 안 걸리는 환자에게 무관한 질환의 예시가 뜨는 문제는 FE 몫이다.
- **복합 경로의 라벨 제거 잔여 조사**(「에게 침 치료해도 돼?」) — 부착 뒤에는 통과한다(실측).
- **복합 답변의 참고안 구조화·의료인 검토** — 다음 스텝이다. 이 스텝으로 두 경로의 스냅샷 참조 방식이 같아진다.
- **검색 게이트 기권 턴의 검색 입력 기록** — 어느 대화에서도 run을 남기지 않는다(§8). 환자 대화는 질문 + 턴 스냅샷으로 재구성된다.
- **환자 맞춤 검색 평가셋** — 이번 측정은 임시 프로브였다. `eval:rag`는 지침 경로만 잰다.
- **PATIENT_GUIDANCE 대화의 에이전트화** — §51 그대로 BE 채팅의 몫이다.
