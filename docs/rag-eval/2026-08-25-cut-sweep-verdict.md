# 리랭크 점수 컷 재판정 — 생성 게이트가 붙은 뒤의 컷 스윕 (2026-08-25)

측정 배경: §40 생성 게이트가 배포된 뒤 `eval:rag`에 컷 스윕을 넣어(#348), 「컷을 낮추면 생성
게이트가 누출을 얼마나 받아내는가」를 처음으로 쟀다. spec 40이 「리랭크 점수 컷 값 변경」의
**선행 조건**으로 지목한 확장이다.

**표본은 프로덕션 평가셋이다** — 운영 덤프 7,154 ACTIVE 청크 × 229문항(answerable 185 /
abstain 44). §29·§31 측정과 같은 코퍼스·같은 문항이라 그 수치들과 나란히 놓을 수 있다.
구성은 운영 정책 그대로(`hybrid-rrf60-top30x2-cut0.48-score9-v4` · gpt-5.4-mini ·
text-embedding-3-small)이고, 생성 프롬프트는 `qa-v6`다.

원자료는 같은 디렉토리의 `2026-08-25-cut-sweep-run1.md` · `-run2.md`다.

## 스윕 읽는 법

컷 c에서 한 문항은 정확히 네 갈래 중 하나다 — 검색게이트(거리 또는 점수 < c) · 생성게이트
(검색 통과 후 `insufficientEvidence`) · 답변 · 생성실패(판정을 못 받음). **컷과 무관하게 전
문항에 생성을 호출**하므로 한 번의 실행으로 컷 전 구간을 사후 재구성할 수 있고, 컷은 라우팅에만
쓰이므로 그 재구성은 **컷 c에서의 운영 동작과 정확히 일치한다.**

## 판정 1 — 컷 전 구간에서 누출이 0이다 (두 번 재현)

| 컷 | ans 검색 (r1/r2) | ans 생성 | ans 답변 | abs 검색 (r1/r2) | abs 생성 | **abs 답변(누출)** |
|---|---|---|---|---|---|---|
| 0 | 0 / 0 | 0 / 0 | 185 / 185 | 9 / 8 | 35 / 35 | **0 / 0** |
| 4 | 0 / 0 | 0 / 0 | 185 / 185 | 26 / 28 | 18 / 15 | **0 / 0** |
| 8 | 0 / 0 | 0 / 0 | 185 / 185 | 36 / 36 | 8 / 7 | **0 / 0** |
| **9 (운영)** | **2 / 0** | 0 / 0 | 183 / 185 | 41 / 41 | 3 / 2 | **0 / 0** |
| 10 | 9 / 11 | 0 / 0 | 176 / 174 | 43 / 43 | 1 / 0 | **0 / 0** |

점수 게이트를 완전히 끄는 컷 0에서도 abstain 44문항이 한 건도 답변으로 새지 않는다. 검색
게이트가 놓친 것을 생성 게이트가 전부 받아낸다.

**이로써 spec 40 판단표의 「컷 8로만 내려도 2건 회수에 5건 누출」이 초과됐다.** 두 수치 자체는
재현됐지만(컷 9→8에서 ans 검색게이트 2 감소 · abs 검색게이트 5 감소, run 1), 그 5건을 abs
생성게이트가 3→8로 흡수해 **순 누출은 0→0**이다. 컷을 다시 볼 사람은 판단표의 그 행을 근거로
쓰지 말 것 — 그 행은 생성 게이트가 없던 시점의 사실이다.

## 판정 2 — 컷은 안전 손잡이가 아니라 비용 손잡이가 됐다

누출이 전 구간 0이므로 컷 선택에서 안전 축이 사라졌다. 남은 축은 둘이다.

| 축 | 컷을 내리면 |
|---|---|
| 과잉 기권 | 줄어든다 — 단 컷 8 이하에서는 이미 0이라 더 얻을 것이 없다 |
| 생성 호출 | 늘어난다 — 기권할 질문이 생성까지 가서 토큰·지연을 쓰고, 사용자는 무관한 근거를 먼저 본다 |

컷 9에서 생성에 닿는 abstain은 2~3건, 컷 8은 7~8건, 컷 4는 15~18건이다. 결과가 같다면 **높은
컷이 싸다.** 컷 3·4는 컷 8과 결과가 동일하면서 생성 호출만 2배라 고를 이유가 없다.

## 판정 3 — 컷 9를 유지한다. 단 이유가 바뀐다

컷 9의 과잉 기권은 **0~2문항(0~1.1%)이고 실행마다 흔들린다** — run 1에서 2건(둘 다 점수 8),
run 2에서 0건이었다. 고정 손실이 아니라 리랭커 점수의 실행 간 변동이다. 컷 8은 두 번 다 0건이지만
이득이 ≤2건이고 매번 나오지도 않는 반면, 대가는 abstain 5건이 더 생성까지 가는 것이다.

**유지의 근거는 더 이상 「9가 누출을 막는다」가 아니다** — 누출은 어디서도 나지 않는다.
지금의 근거는 「생성 호출을 가장 아끼고, 과잉 기권 ≤2건은 감수한다」다. 코드 변경은 없다
(`retrieval.config.ts` 기본값이 이미 9).

## 판정 4 — 생성 게이트의 과잉 기권이 두 번 다 0이다

발화는 run 1에서 43건, run 2에서 42건이었고 **전부 abstain**이다. answerable 185문항에서 생성
게이트가 잘못 발화한 건은 한 번도 없다. spec 40이 「이 설계의 주 리스크」로 지목하고 실험
레포에서 24문항 중 1~2건 관측했던 과잉 기권이, 프로덕션 185문항에서는 관측되지 않았다.

원인 라벨도 한쪽으로 몰렸다 — 두 실행 모두 `model_verdict` 100%, `empty_aspects` **0건**이다.
spec 40이 「원인 분포가 드러난 뒤에 처방을 고른다」며 미뤄둔 빈 축 재호출·무효화는, 이 코퍼스에서
다룰 사례 자체가 없다.

## 유보 — 이 판정을 뒤집을 수 있는 것

- **독립 시험셋이 아니다.** 이 229문항은 컷 9 결정(#232·#246)에 쓰인 바로 그 평가셋이고, abstain
  문항이 「무엇이 샜는가」를 보고 보강된 이력이 있다. 결론이 이 셋에 과적합됐을 수 있다.
- **2회 실행이다.** 벡터 순위 지표(Recall@5 0.843 · MRR 0.714 · Recall@30 0.968)는 두 번 완전히
  같았지만(LLM 무관), 리랭크·생성이 걸린 축은 움직였다 — 컷 9의 과잉 기권 2↔0, 컷 10의 9↔11.
- **실트래픽 분포는 모른다.** abstain 문항은 역생성·수기 작성한 인접 임상 질문이다. 프로덕션
  ASSISTANT 메시지는 63건뿐이라(§40 실측) 실제 기권 질문의 분포를 대표한다고 말할 수 없다.
- **리랭커 타임아웃은 재시도되지 않는다.** run 2에서 1건(`evalgen-abstain-002`)이 첫 응답
  타임아웃 10초로 실패했다. #352의 재시도는 429만 다루고, `openai-reranker.ts`에는 자체 재시도가
  없다(`withRetry`는 `LlmGateway` 전용). 229문항 중 1건(0.4%)이라 이 판정을 바꾸지 않지만,
  리포트가 답변으로 섞지 않고 「생성실패」로 따로 세기 때문에 확인 가능한 것이다.
